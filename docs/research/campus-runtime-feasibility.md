# 校舎PCの性能再現と5分制限の調査

状態: 2026-11-11の診断。所有者は同日、自動連続負荷・安全停止を伴う改修とVMを候補に含める方針を承認。
判断の選択肢は[ADR-0022](../design/adr/0022-campus-runtime-calibration.md)に記録する。

## 目的と要件

[Subject v1.7](../subject-v1.7.md)のV.5は「標準的なハードウェアで全テストプロンプトを5分未満」とする。
ハードウェアの定義、テスト件数、モデルロードを含むかは未定義である。
本調査は校舎のCPU実行を対象とし、モデルがキャッシュ済みの状態で、
`uv run python -m src`の起動から正常終了までを測る。判定は300秒未満とする。
依存の取得・モデルのダウンロードは別記録にする。この境界はプロジェクトの評価方針で、Subjectの追加要件ではない。

開発機の実行時間から校舎での所要時間を見積もりたい。そのために必要なのは、
対象入力と熱状態を明示した性能の近似である。CPU名や温度表示が同じVMを作ること自体を達成条件にはしない。
未知のテスト件数・入力長に対して、有限の測定だけで5分未満を保証することはできない。
精度・スキーマ適合性の評価と時間測定は分ける。

4スレッドでは読込が近づいても、コピーは約半分の時間で、64行の計算は約2.1倍の時間がかかる。

このNumPy負荷から、PyTorch/Qwenの全処理時間や低速側の上限を直接導くこともできない。

## 現在の情報で再現できる範囲

| 対象 | 現時点の診断 |
| --- | --- |
| Python・依存・入力・モデル・SDK | 版とハッシュ、起動条件をそろえる環境は作れる。今回のJSONにはモデル・SDK・実アプリ入力の情報がない |
| CPU割当・スレッド数・メモリ容量制限 | 開発機で制限できる。これは校舎のCPU構造やメモリ帯域の再現を意味しない |
| 対象アプリの処理時間 | 同一入力で実機と開発機を測り、別入力で検証すれば、検証範囲を明示した近似を作れる見込みがある。現時点では未検証 |
| i7のP/Eコア、キャッシュ、命令ごとの速度 | AMD上の通常のVMで同じになるとは扱えない |
| 校舎の温度、ファン制御、熱による性能低下 | 現在のデータでは予測不能。VM内の実行も開発機自身の冷却・電力条件に影響される |
| Subjectの全テスト5分未満 | 件数・入力規模が未定義なので未判定。既知11件の成功を全テストへ外挿しない |

QEMU/KVMのCPU設定はゲストへ見せる命令機能などを指定する。
そこからIntel実機の命令実行時間や冷却挙動まで得られるとは解釈できない。
QEMUのTCGも命令の実ハードウェア上の所要時間を模倣する仕組みではないと公式文書に明記されている。
詳細なCPU・熱シミュレーターを別途校正する方法は考えられるが、今回の5分判定のために採用する根拠は乏しい。
出典: [QEMUのCPU設定](https://www.qemu.org/docs/master/system/qemu-cpu-models.html)、
[TCGと実行時間](https://www.qemu.org/docs/master/devel/tcg-icount.html)。

## 温度と性能低下について分かったこと

今回のJSONの校舎温度は開始54℃・終了80℃、開発機は開始40.75℃・終了76.75℃だった。
スクリプトはCPUセンサーの最大値を取得するが、開始・終了時に最大となったセンサーが同じかは記録しない。
開始終了の2点では、途中の最高温度・上昇率・冷却時間・処理ごとの温度は分からない。
5サンプルは短いバッチの反復であり、5分近い実アプリ負荷や熱の定常状態を測ったものではない。
固定順で処理・スレッド設定を測るため、設定の差と熱の持ち越しも分離できない。

既存の`research/campus/pc-hdad92b5bf4f3.txt`には、別のSDK測定で最高97℃、
`bench.env.throttle_events=7788`が記録されている。
この値はcore/packageカウンターを合計した差分で、独立した7788回の事象や7788秒を意味しない。
校舎のSDK負荷で熱による制限を観測した根拠にはなるが、今回のアプリの減速率は導けない。
別途提供されたアプリ65.74/71.41/71.49秒と100℃の情報は原票・入力・commitが未確認である。
温度だけでクラッシュ・停止の原因や性能低下率を断定しない。

温度の予測には、消費電力の時系列、開始温度、室温、冷却器とファンの応答、
電力制限とその時間窓、CPU内部の熱保護の条件が必要になる。
CPU名・使用率・TDPだけでは何秒後に何℃になるかを定められない。
5分判定では、校舎の実アプリ負荷について温度と処理速度を同時に観測する方が直接的である。
周波数低下は温度以外にも電力制限・負荷配分・OS方針で生じるため、要因を分けて記録する。

## 追加して取得する情報の提案

| 情報 | 用途・取得できない場合 |
| --- | --- |
| 匿名PC ID、UTC、commit、調査器・SDK・uv.lock・入力のハッシュ | 測った対象を結び付ける。本文・ユーザー名・ホームパスは公開レポートへ入れない |
| CPU family/model/stepping、P/E・SMT・共有キャッシュの対応、許可CPU | 校舎の28論理CPUと開発機のコア割当の違いを把握する。コア種別が読めなければ不明とする |
| OS・kernel、Python、NumPy/BLAS、torch/transformers、CPU実行・dtype・スレッド条件 | 同じ計算条件かを確認する。`powersave`という名前だけで低周波数固定と判断しない |
| 利用可能メモリ、cgroupのCPU・メモリ・swap制限、PSI、page fault、swap使用 | 容量不足・割当制限・待ち時間を熱による減速と区別する |
| 同一センサーごとの温度・label・crit値、時刻、core/package別thermal counter | 温度曲線と熱制限の発生を対応付ける。共通の100℃判定を全CPUへ使わない |
| 周波数の値と取得元、RAPL電力量・電力制限と時間窓 | 熱制限と電力制限の候補を分ける。権限不足なら欠測にする。要求周波数を実効周波数と呼ばない |
| 実行全体の壁時間、終了コード、プロセス群のCPU使用・RSSサンプル、ホスト全体の負荷 | アプリの時間と他の負荷を対応付ける。RSSのサンプル最大値は真の瞬間ピークと区別する |
| 入力件数・文字数分布、関数・引数数、生成量・forward入力長 | 大きい入力への外挿に必要。最小の観測モードではforward数を自動取得しないため、未知負荷への予測は保留する |

物理的な冷却条件をモデル化する場合には室温・ファン回転・メモリの規格やチャネル構成も調べるが、
最初の改修で管理者権限の取得やSMBIOS情報の全出力は行わない。
公開情報に足りない項目は、測定値と区別した手動メモとして補う。
sysfsに項目がない場合と権限不足を区別し、0として保存しない。

出典: [coretemp](https://docs.kernel.org/hwmon/coretemp.html)、
[センサーABI](https://docs.kernel.org/hwmon/sysfs-interface.html)、
[intel_pstate](https://docs.kernel.org/admin-guide/pm/intel_pstate.html)、
[RAPL](https://docs.kernel.org/power/powercap/powercap.html)、
[cgroup v2](https://docs.kernel.org/admin-guide/cgroup-v2.html)。

## 承認後の追加調査

所有者の指示に従い、通常開始温度と温まった開始温度を人が作り分ける手順を改めた。
スクリプトが固定入力長のSDK forwardを連続実行し、自らの負荷で温まる過程を観測する。
入力長ごとの処理時間と温度時系列を残し、安全停止に達するまでの範囲を比較する。
熱スロットリング、温度上限、監視不能、メモリ不足を検知したら停止し、自動再開しない。
具体的なCLI、閾値、停止・保存の契約は[連続負荷の設計](../superpowers/specs/2026-11-11-safe-thermal-survey.md)にある。

実装上の選択として、既にdevelopにあるcampus_surveyの調査機能を再利用する。
未統合のhardware_probeへ大きな変更を重ねず、thermalコマンドから専用モジュールへ委譲する。
既存のNumPy比較とSDK benchmarkの形式は保持する。
この固定SDK負荷は、実アプリの5分未満の判定や未知入力への外挿を代替しない。
熱に起因する減速率は、温度・電力・counter・処理時間を照らし合わせて判断する。

## 仮想環境の選定

VMはOSの分離だけでなく、CPU・メモリ・swap・依存の設定をひとまとまりで管理できる利点がある。
この利便性も含めてcgroupと対等に候補へ入れるという所有者の意見を反映する。
両方で同じ固定SDK負荷と実アプリを測り、誤差と構成管理の容易さを確認して選ぶ。
採用する許容誤差と300秒に対する余裕は所有者が決める。
調整に使う入力と検証用の入力は分け、都合のよい外れ値除外はしない。

VM案では、校舎と同じOS・Python・依存・モデルをゲストへ用意し、メモリ割当・vCPUのホストコア固定・swapを設定する。
物理温度と熱制限はホストで監視し、ゲスト側では負荷と時間を測る。
ゲスト内に温度・counterが見えない状態で安全確認済みとはしない。
ホストのQEMU全体にCPU割当制限を掛ける場合は、I/O等のスレッドも対象になる点を確認する。
CPU数の表示を合わせるだけでP/Eコア・キャッシュ・冷却特性は一致しない。

この調査時のsandboxには/dev/kvmが見えず、VM作成・起動は確認していない。
ホスト全体にKVMがないとは断定せず、ホストでデバイス・権限・センサーの可視性を確認する。
今回の測定器にVMの作成・起動・遠隔停止は含めない。
出典: [cgroup v2](https://docs.kernel.org/admin-guide/cgroup-v2.html)、
[QEMU起動設定](https://www.qemu.org/docs/master/system/invocation.html)。

既存の「phys16-t6の総時間＋8秒」は所有者が採用した既知11入力用の暫定見積もりとして保持する。
新しいraw値へ8秒を加えて保存したり、NumPy・forwardごとに加えたり、待機を挿入したりしない。
今回の5処理の比率は、この暫定見積もりを別入力で検証した結果ではない。

## 未確認事項と今後の判断

- 校舎での連続負荷の実測値と、安全停止までの温度・時間の関係。
- 校正を採用する許容誤差、300秒に対する時間の余裕、検証する入力規模。
- VM/cgroupの採用。今回の温度・counter表示は、連続負荷の監視として提供する。
- 校舎での追加測定、観測器の影響、実効周波数・RAPL等の取得権限、VM起動。

所有者からは、この後に校舎PCでコマンドを実行して結果を持ち帰れるとの回答を得た。
このセッションから校舎PCへ接続して追加測定した事実はない。
