# 校舎PCの性能再現と5分制限の調査

状態: 2026-11-11の診断と追加調査の提案。スクリプト変更・VM作成は未承認、未実装。
判断の選択肢は[ADR-0022](../design/adr/0022-campus-runtime-calibration.md)に記録する。

## 目的と要件

[Subject v1.7](../subject-v1.7.md)のV.5は「標準的なハードウェアで全テストプロンプトを5分未満」とする。
ハードウェアの定義、テスト件数、モデルロードを含むかは未定義である。
本調査は校舎のCPU実行を対象とし、モデルがキャッシュ済みの状態で、
`uv run python -m src`の起動から正常終了までを測る。判定は300秒未満とする。
依存の取得・モデルのダウンロードは別記録にする。この境界はプロジェクトの評価方針で、Subjectの追加要件ではない。

開発機の実行時間から校舎での所要時間を見積もりたい。そのために必要なのは、
対象入力と熱状態を明示した性能の近似である。CPU名や温度表示が同じVMを作ること自体を達成条件にはしない。
未知のテスト件数・入力長に対して、有限の測定だけで5分未満を保証することはできない。
精度・スキーマ適合性の評価と時間測定は分ける。

詳細なCPU・熱シミュレーターを別途校正する方法は考えられるが、今回の5分判定のために採用する根拠は乏しい。

## 温度と性能低下について分かったこと

今回のJSONの校舎温度は開始54℃・終了80℃、開発機は開始40.75℃・終了76.75℃だった。
スクリプトはCPUセンサーの最大値を取得するが、開始・終了時に最大となったセンサーが同じかは記録しない。
開始終了の2点では、途中の最高温度・上昇率・冷却時間・処理ごとの温度は分からない。
5サンプルは短いバッチの反復であり、5分近い実アプリ負荷や熱の定常状態を測ったものではない。
固定順で処理・スレッド設定を測るため、設定の差と熱の持ち越しも分離できない。

既存の`research/campus/pc-hdad92b5bf4f3.txt`には、別のSDK測定で最高97℃、
`bench.env.throttle_events=7788`が記録されている。
この値はcore/packageカウンターを合計した差分で、独立した7788回の事象や7788秒を意味しない。
校舎のSDK負荷で熱による制限を観測した根拠にはなるが、今回のアプリの減速率は導けない。
別途提供されたアプリ65.74/71.41/71.49秒と100℃の情報は原票・入力・commitが未確認である。
温度だけでクラッシュ・停止の原因や性能低下率を断定しない。

温度の予測には、消費電力の時系列、開始温度、室温、冷却器とファンの応答、
電力制限とその時間窓、CPU内部の熱保護の条件が必要になる。
CPU名・使用率・TDPだけでは何秒後に何℃になるかを定められない。
5分判定では、校舎の実アプリ負荷について温度と処理速度を同時に観測する方が直接的である。
周波数低下は温度以外にも電力制限・負荷配分・OS方針で生じるため、要因を分けて記録する。

## 実装を提案する最小の変更

既存の`tools/hardware_probe.py`に、実アプリを子プロセスとして起動して観測する`observe`を追加する案を勧める。
`measure`と`compare`の既存protocol 1と既存の原記録は変更しない。
新しい観測レポートは専用のversionを持ち、短いNumPy負荷の結果と混ぜない。
データフローは「対象と実行条件の記録 → 指定コマンドの実行 → 1秒ごとの観測 → 終了・予算超過の記録 → JSON保存」とする。
これは提案であり、以下のCLIはまだ存在しない。

```text
.venv/bin/python -m tools.hardware_probe observe \
  --pc-id cmm-007 --budget 360 --output /tmp/campus-runtime.json \
  --input data/input/function_calling_tests.json \
  --input data/input/functions_definition.json \
  -- uv run --no-sync python -m src --output /tmp/campus-calls.json
```

モデルは既存キャッシュをオフラインで使う。校舎には開発機用のCPU・容量・冷却待ち制限を掛けない。
親は単調時計でアプリの開始から終了までを測り、メタデータ収集・事後のJSON保存時間を別にする。
stdout/stderrを引き継ぎ、端末へ出す実行条件をそろえる。出力ファイルのパスは毎回変える。
新規レポートは既存ファイルを上書きせず、途中終了時にも取得済みデータと未完了状態を残す。
タイムアウト・割り込み時は専用プロセス群へSIGTERMを送り、最大5秒の猶予後にSIGKILLして回収する。
360秒はコマンド実行の予算、停止猶予はその外側とし、開始終了時刻・停止理由を別に記録する。
予算超過・途中終了を成功扱いせず、合格線は300秒未満のままとする。

観測するのは読み取り可能な`/proc`と`/sys`、対象プロセス群のみである。
CPU governor、ファン、電力上限、スレッド数、cgroupの設定は観測モードから変更しない。
他ユーザーの個別プロセス情報・環境変数一覧・生の例外・任意コマンド引数はレポートへ保存しない。
RAPLはラップアラウンドと欠測を扱い、CPU割当による`cpu.stat`の制限とthermal counterを別の項目にする。
対象外のセンサーをCPU温度として代用せず、取得不能は理由付きで残す。

最初の版では生成ループへ計測コードを挿入せず、`src/`・SDK・依存関係を変更しない。
この版で測れる減速は、同一入力の通常開始時と温まった開始時の総時間の差である。
1回の実行の途中で単位処理あたりの速度が何％落ちたかは、CPU使用率と周波数だけでは測れない。
その確認が必要なら、同じ入力長の公開SDK呼び出しを繰り返して区間ごとの時間を測るか、
実アプリのプロンプト・forwardごとの処理量と時刻を記録する追加設計が必要になる。
実アプリで時間が変わる原因を絞れない場合は、公開SDK APIによる入力長別の追加測定と
forward入力長・回数を記録する設計を別途提案する。
1秒ごとの観測自体の負荷もあるため、観測あり・なしの実行を交互に測って差を残す。

変更対象はprobe、対応テスト、probe説明、校舎・開発機の手順、開発用文書と測定方針である。
対象probeは`origin/develop`へ未統合なので、実装前に統合先との依存関係を確認する。
この文書変更のためにfeatureや実験ブランチをマージしない。
以前の測定方針には校舎の常時表示器を校舎側で後日作る方針があるため、
今回の汎用観測モードで置き換えるかも、承認対象に含める。

テストは固定時刻・偽のsysfsデータで単位、温度の対応、欠測・権限不足、カウンター差分を先に確認する。
小さい実プロセスで正常終了・失敗・タイムアウト・割り込みとレポート保存を確認する。
実装後は`make install`・`make lint`・`make test`と独立レビューを行う。
開発機で観測器が動いても、校舎の温度曲線や性能再現が確認できたとは扱わない。

## 校舎で行う測定と、仮想環境の作成構想

1. 同じcommit・入力・モデル・SDK・依存で、対象の全プロンプトを校舎CPUで実行する。
   通常開始温度からの1回と、直前の実行で温まった状態の回を分け、実行間隔と開始温度を残す。
   各条件を最低3回、単独実行する案とし、全結果・中央値・範囲を保存する。任意の外れ値除外はしない。
2. 短い入力・長い入力、多い関数・引数、長い生成など、実装が受け付ける範囲の負荷を用意する。
   対象入力の規模を先に決めて記録する。設定を合わせる入力と、調整に使わない検証入力を分ける。
   5分近い負荷の温度曲線を確認し、同一入力の通常開始時と温まった開始時の総時間を比較する。
   異なる入力の実行前半・後半の時間差を、そのまま熱による減速率にはしない。
   連続実行による熱の持ち越しは頑健性の追加調査で、Subjectの明文要件とはしない。
3. 開発機では既存の独立したCPU用venvを使い、モデル・依存を固定する。
   `taskset`で使用コアを選び、`systemd-run --user`のcgroupでメモリ・swapと必要ならCPU時間を制限する。
   メモリ上限は校舎の物理16GBを丸めるだけで決めず、実測した利用可能量・圧迫状態を確認する。
   スレッド数、コア選択、CPU割当を候補として測る。制限を掛けた後にもう一度各処理を測る。
4. 調整に使わなかった入力・温度条件で、校舎と開発機の差を検証する。
   事前に人間が許容誤差と時間の余裕を決め、最大の過小見積もりを報告する。
   誤差が負荷ごとに変わるなら、単一の再現設定は採用せず、校舎で直接測る。
   観測した誤差と余裕は未観測入力への数学的な保証にはならない。
5. OSまで分離する必要が出た場合は、校舎と同じディストリビューション・PythonのKVMゲストを作り、
   メモリ割当、vCPUのホストコア固定、swap、依存・モデル・入力を固定する。
   ゲストのCPU機能はホストで利用可能なものに限定し、ゲスト内でも同じ測定・検証を繰り返す。
   ホストのCPU時間上限を使う場合はQEMUのI/O等のスレッドも対象になる点を確認する。
   CPU数を28と表示させるだけでは、校舎のP/Eコア構成の再現にはならない。

推奨は手順1〜4のcgroupによる近似と実機確認である。
VMはOSの分離が必要な場合の選択肢とし、校舎の熱挙動を検証する手段にはしない。
この調査時のsandboxには`/dev/kvm`が見えず、VM作成・起動は確認していない。
ホスト全体にKVMがないとは断定できない。実機側でデバイス・権限・仮想化機能を確認する必要がある。
出典: [cgroup v2](https://docs.kernel.org/admin-guide/cgroup-v2.html)、
[QEMU起動設定](https://www.qemu.org/docs/master/system/invocation.html)。

既存の「phys16-t6の総時間＋8秒」は所有者が採用した既知11入力用の暫定見積もりとして保持する。
新しいraw値へ8秒を加えて保存したり、NumPy・forwardごとに加えたり、待機を挿入したりしない。
今回の5処理の比率は、この暫定見積もりを別入力で検証した結果ではない。

## 未承認の判断と未確認事項

- 追加する最小機能を`observe`とし、実機の実アプリ測定を優先するか。
- 校正を採用する許容誤差、300秒に対する時間の余裕、検証する入力規模。
- 別途の常時表示器と今回の観測モードの役割、実装時のブランチ依存。
- 校舎での追加測定、観測器の影響、実効周波数・RAPL等の取得権限、VM起動。

所有者からは、この後に校舎PCでコマンドを実行して結果を持ち帰れるとの回答を得た。
このセッションから校舎PCへ接続して追加測定した事実はない。

## この文書変更の検証

専用worktreeで`make install`・`make lint`（25ファイル）・`make test`（53件）が成功した。
調査対象のfeatureブランチでは既存probeの14テストと、取得した実データの比較を実行した。

レビューで指摘された実行中の処理速度の計測限界と、停止猶予の契約を設計へ追記した。
これらは追加する観測モードや校舎の性能近似を検証した結果ではない。
