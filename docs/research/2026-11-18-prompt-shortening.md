# 入力プロンプト短縮の実験（2026-11-18）

所有者の依頼「入力プロンプト短縮の性能・精度実験」の記録。実験と分析だけを行い、製品コードは変えていない。
採用は決めていない（判断は所有者が行う）。

## 前提と方法

- 対象の製品コードは `baeba96`（方式B・固定JSONの空白削減を含む）。
- 条件の切り替えは実験用スクリプトだけで行った。`pipeline.build_parameters_prompt`の差し替え（実験1）と、
  `Model.logits`へ渡す入力の先頭（プロンプト部分）の差し替え（実験2）である。
  スクリプトは`../measurements/2026-11-18-prompt-shortening/prompt_exp.py.txt`。
- 精度: GPU（`.venv-gpu`）、既存4集合30件（standard11 + 回帰19件）。5条件を並列に実行した（精度のみ。時間の測定ではない）。
- forward回数・各forwardの入力長は、実行中に`Model.logits`へ渡された入力から数えた実測値。
- 時間は、t6でのCPUの近似式 t = 0.0791·F + 0.001984·L 秒（F: forward回数、L: 入力長の合計）による**推定**。
  CPUでの実測・再生は行っていない。校舎PCでも測っていない。
- 条件Aの文字列は製品の`build_parameters_prompt`と一致することをスクリプト内で確認した。
  Aの集計は前回の方式Bの記録（標準11件で514 forward、入力長の合計113025）と一致した。

## 6. 問題点と失敗の例

- **C・D（関数の説明文を除く）**: 正規表現の書き方が`\d+`から`([0-9]+)`へ変わった。
  説明文の「regex」などの語が、表記の選び方に効いていると推測する（未検証）。
  Dでは、文字列に引用符が付いたまま値になった（changed-2）。関数名も除くと、引数の意味の手がかりが減ると推測する。
- **DYN（依頼文を途中で除く）**: standard-09で、パターンではなく依頼文中の数字`34`をそのまま書いた。
  依頼文は出力JSONの`prompt`欄に残っている。それでも、ユーザーの発話として読めなくなると、指示の「依頼から抽出する」が弱まると推測する（未検証）。
  技術的には、確定済みIDを保ったまま、前に付けるプロンプトIDだけを替えられた。ただし生成の途中で会話の構造が変わる。
  切り替え時点（`prompt`欄の確定）は、出力のバイト列で判定した。
- **B（戻り値の型を除く）**: 正答から誤答への変化はなかった。変化したのは、もともと誤答の2件だけ。

## 7. 最も有望な案と、採用の判断に必要な未検証事項

- **最も安全な案はB**（戻り値の型を除く）。30件で正答の入れ替わりはなく、推定で約−8秒。
- 推定の削減量が大きいのはD（約−22秒）とC（約−16秒）。ただし完全一致では、standard-09（標準11件の1件）を失う。
  C・Dで standard-09 を失うのは、意味は同等の表記の違いで、置換の結果は同じ。
  ただし採点が完全一致なら、この違いでも失点になる。
- DYNは、正答から本当の誤りへの変化（standard-09）があり、推定の削減量もDより小さい。勧めない。
- 実験3（system指示の簡略化）は実施していない。system指示は120トークンで、プロンプトの約6割を占めるため、削減の余地は最も大きい。
  ただし過去の誤答への対策を含むので、1文ずつ外して比べる必要がある。次の候補として残す。

採用の判断に必要な未検証事項:

- CPU（t6）での実測、または再生による時間の確認。上の秒数はすべて近似式による推定である。
- 30件以外の未見の入力（意味の似た引数名、複数の文字列引数など）での精度。今回は既存の30件だけを使った。
- B〜Dと他の短縮の組み合わせ（依頼に従い、同時には適用していない）。
- 校舎PCでの時間。
