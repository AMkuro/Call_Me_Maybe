# 引数抽出の指示文の短縮（実験3、2026-11-18）

所有者の依頼「実験3（引数抽出用system指示文の短縮）」の記録。実験と分析は製品のプロンプトを変えずに行った。
その後、所有者が推奨構成c1Bの採用を決めた（2026-11-18）。製品への反映は`docs/architecture.md` §3.2にある。

## 前提と方法

- 対象の製品コードは `2e4b0af`（方式B、固定JSONの空白削減、thinkブロックあり）。
- 条件の切り替えは実験用スクリプト（`../measurements/2026-11-18-instruction-shortening/instr_exp.py.txt`）だけで行った。
  `pipeline.build_parameters_prompt`を差し替え、system指示だけを変える。
  指示文は、すべての関数と入力に共通の固定文である。入力・関数名・キーワードによる切り替えはない。
- 未変更の指示文が製品の`PARAMETER_INSTRUCTIONS`と一致し、Aのプロンプトが製品の`build_parameters_prompt`と一致することをスクリプト内で確認した。
- 精度: GPU（`.venv-gpu`）、完全一致の評価。複数の条件を並列に実行した（精度のみ。時間の測定ではない）。
  正規表現は、fixtureの`regex_checks`（別の入力への置換結果）による意味の比較を、完全一致とは別に記録した。
- 入力長: SDKの実トークナイザーで数えた。forward回数と各forwardの入力長は、`Model.logits`へ渡された入力から数えた実測値。
- 時間: t6でのCPUの近似式 t = 0.0791·F + 0.001984·L 秒による**推定**。CPUでは測っていない。

### 評価集合と段

| 段 | 集合 | 件数 | 位置づけ |
|---|---|---:|---|
| 1 Subjectの水準 | standard11、calibrated（original + boolean・difference・feature_flags・magnitude・timer_flags・transfer・word_pairs） | 88 | 採否の主な根拠 |
| 2 型と形式の堅牢性 | changed5、未見のu01・u02・u06・u08〜u12 | 13 | 退行の確認 |
| 3 限界の確認（参考） | boundary3、未見のu03・u04・u05・u07 | 7 | 参考 |

- calibratedの7集合（boolean〜word_pairs）は、2026-11-11に作られた入力ファイルで、実モデルでの評価は今回が初めて。
- 未見の12件（`unseen12.json`）は、実験3の実行前に作り、結果を見てから変えていない。
  Subjectの例より難しい問題（依頼文に「regex」と書かずに正規表現を求める、前後の空白を保つなど）を含むため、第3段に分けた。
- 7集合は、A・B・c1・c2・c2Bとc1Bだけで実行した。1文を外す条件は、42件（7集合以外）だけで実行した。
  同じコードとプロンプトなら出力は再現する（Aが前回の記録と一致した）。そのため42件は再実行していない。

## 1. 指示文の役割と削除の可否

| 文 | 内容 | トークン | 1文だけ外した結果（42件） | 判定 |
|---|---|---:|---|---|
| S1 | The user request will be fulfilled by calling the given function. | 12 | 退行なし | S2に意味が含まれる（推測）。ただしS2の「that call」が指す先になる |
| S2 | Extract the arguments … copy each value as it appears …; do not answer the request or compute a result. | 31 | 退行なし | **残す**。「計算しない」の意味を保つ条件があるため。短く言い換えると数値が終わらなくなった（下記c2） |
| S3 | Keep the requested input values and strings exact. | 9 | 退行なし | S2の「copy each value as it appears」に含まれる（推測） |
| S4 | Return only a JSON object with prompt, name, parameters. | 12 | **5件を失った**（4件は256トークン上限） | 残す |
| S5 | Use JSON numbers, strings, true/false. | 9 | **standard-09を失った**（regex `34\|233`） | 残す |
| S6 | Convert descriptions of patterns into actual regular expressions …. | 17 | **standard-09を失った**（regex `34\|233`） | 残す |
| S7 | Express replacement symbols as their literal characters. | 8 | 退行なし | 効果は見えない。replacementは前後とも誤答の件で値が揺れるだけ |
| S8 | Do not add leading or trailing whitespace …. | 15 | 退行なし | 効果は見えない（未見u05の空白保持は、Aでも失敗している） |
| S9 | Preserve numeric signs and decimal points. | 7 | 退行なし | 効果は見えない（負号の脱落u01・u02・u09・transfer-07は、Aでも起きている） |

S7〜S9は、過去の誤答への対策として足された文である。今回の集合では、あってもなくても結果は変わらなかった。
これは「必要ない」ことの証明ではなく、「今回の入力では効果が測れなかった」ことを意味する。

## 3. Aと比べて退行しなかった候補

- 1文: −S1、−S2、−S3、−S7、−S8、−S9（42件のみ）。ただし−S2は「計算しない」の意味を失うため、条件を満たさない。
- 組み合わせ: c1、c1B、B（119件）。

## 4. 現行製品（A）で見つかった問題（短縮とは別）

- 第1段で80/88（90.9%）。7集合だけでは61/77（79%）で、Subjectの90%を下回る。
- 7集合の正規表現21件のうち14件が誤答。「numbers」は`6|12`・`digits`などに、「vowels」は`aeiou`になる。
- timer-flags-01で数値が終わらず、256トークンの上限に達した（JSONが出ない）。Subjectの100%有効JSONの要件に関わる。
- transfer-07（-14の絶対値）で`14`を出した（計算した結果を引数にしている）。
- 未見の第2段で負号が落ちた（u01 `3.5`、u02 `0.004`、u09 `12.0`）。

## 5. 採用のリスク

- 評価件数が少ない。c1とAの差は第1段で+1件で、偶然の範囲と考える（推測）。
- 1文を外す条件は、7集合では実行していない。c1・c1Bの7集合の結果で、組み合わせとしての退行がないことだけを確かめた。
- c1では、S2の「that call」が指す先（S1）がなくなる。精度への影響は見えなかったが、文として読みにくい。
- S7〜S9の役割は、今回の集合では測れなかった。過去の誤答の原因になった入力が再び来ると、効く可能性がある。
- 数値の終わり方が、プロンプトのわずかな違いで崩れる（S4、S2の言い換え、c2B）。短縮の副作用は、上限到達として現れやすい。
- 時間は推定で、CPUと校舎PCでは測っていない。

## 6. 推奨構成

**c1B（S1・S3・S7・S8・S9を外し、Bを組み合わせる）を第一候補として提案する。**

- 根拠: 119件で、Aから失った件がない。第1段の正答はAと同じ80/88。標準11件の推定forward時間は−53.3秒。
- 次点はc1（Bなし）。第1段で81/88、推定−47.9秒。Bの効果（−5.4秒）を見送る場合の候補。
- 採らない: c2・c2B（数値が終わらず、Aが解ける件を失う）、−S4・−S5・−S6（正答を失う）、−S2（意味の条件を満たさない）。

採用を決める前に確かめたい点:

1. CPU（t6）での時間（上の秒数はすべて推定）。
2. S2の「that call」を言い換えた版の精度（読みやすさのため。未実施）。
3. 現行製品の問題（正規表現、数値の上限到達、負号）への対処。これは短縮とは別の課題で、短縮の採否より優先度が高いと考える（推論）。
