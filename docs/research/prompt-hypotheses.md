# プロンプト改善実験の仮説と根拠

調査日: 2026-11-10。対象: Qwen3-0.6B、英語の指示、現在の2段階の制約付き生成。
状態: 実験候補。採用の決定、実装変更、モデルでの比較実験は行っていない。

最初に比較する候補は、入力引数の役割の明示、値の保持規則、短い正解例、
関数一覧の書式である。現在の誤答に対応し、生成処理を変えずに比較できるため、この順を推奨する。
以下では、文献の報告、このリポジトリでの観測、そこから立てた仮説を区別する。
文献の結果だけでは、この実装で改善するとは判断できない。

## 対象となる処理と既知の誤り

比較の基準はコミット `58adc5468aeafbe3e1b8d4e9629e0cabd0c07e3c` の
[prompt.py](../../src/prompt.py) とする。
モデルのリビジョンは `c1899de289a04d12100db370d81485cdf75e47ca`。

| 段階 | モデルに渡す情報 | モデルが選ぶ内容 | 比較する正しさ |
| --- | --- | --- | --- |
| 名前選択 | 全関数の名前・説明・引数名と型、依頼文 | 名前の木で許されるトークン、EOS | 意図に合った関数か |
| 引数生成 | 選択した関数の定義、依頼文、途中まで書いたJSON | 型の文法で許される値と終端 | 渡すべき引数か |

現在の引数生成では、依頼文がuserメッセージとassistant側のJSONの`prompt`欄に現れる。
`prompt`欄はコードがコピーし、キー・区切り・引数順もコードが強制する。
関数定義には`returns`も提示するが、アプリケーションは関数を実行しない。
入力の引数定義にある情報は名前と型で、引数ごとの説明欄はない。
詳しい契約は[設計書](../architecture.md)を参照する。

[既存の測定](../implementation-verification.md)では、調整後の配布サンプルが10/11件、
変更した関数セットが3/5件の完全正答だった。残った誤りには、`Enable the feature.`での
`heartbeat`選択、`-12.75`の負号欠落、置換文字列への余計な先頭空白がある。
このデータは既に調整に使っているので、後述する未使用の評価集合には数えない。

構造の妥当性と意味の正しさは別に測る。
[StructureBench（IJCAI 2026）](https://ijcai.org/proceedings/2026/267)は、
Qwen3-0.6Bを含む小型モデルで構造生成を評価し、構文適合だけでは意味の正しさを保証しないと報告している。
同じモデル名でも、同論文のデータ・制約ライブラリ・実行条件は本実装と異なる。
今回の調査は精度改善の準備であり、基盤実装PR #44の承認条件を変更するものではない。

## 比較候補

### H01: 入力引数の役割を明示すると、計算結果との混同が減る

**仮説。** 冒頭で「関数に渡す入力値」を定義すると、関数の結果を答える誤りが減る。
これは本タスクへの推測である。
[Anthropicのツール設計記事（2025）](https://www.anthropic.com/research/writing-tools-for-agents)は、
説明を改善して不要な引数加工を減らした実例と、実際の呼び出し記録から説明を調整する方法を示している。
Claudeを使ったエージェントでの経験であり、Qwen3-0.6Bでの効果量は示していない。

**比較。** 引数生成の冒頭`Extract arguments for the selected function; do not execute it.`だけを、
次の文に置き換える。他の指示、関数定義、書式は固定する。

```text
Fill the selected function's input parameters from the request.
The parameters are the values passed into the function.
```

**判定。** 足し算なら答えでなく2つの被加数、置換なら置換後の文章でなく対象文字列・パターン・置換値を
返せるかを比較する。新しい関数セットでも「結果を引数に入れた誤り」が減ると支持する。
その誤りが減らなければ、この言い換えの優先度を下げる。入力トークン数は少し増え得る。

### H02: 値を保持する規則をまとめると、符号・空白の誤りが減る

**仮説。** 別々に追加してきた注意書きを、保持する値と変換する値の区別にまとめると、
負号や文字列端の空白を保ちやすくなる。直接の根拠は既存の誤答であり、
「肯定形なら常に優れる」という一般則を文献から主張するものではない。

**比較。** 名前選択やJSONの指示は固定し、引数生成にある値保持の3文
（`Keep the requested...`、`Do not add leading...`、`Preserve numeric...`）だけを次に置き換える。
正規表現・置換記号の表現変換を求める既存の指示は維持する。

```text
Copy explicitly supplied numeric and string values exactly, including
numeric signs, decimal points, and spaces inside string values.
```

**判定。** 正負の対、小数、空文字列、先頭・末尾空白、引用符、バックスラッシュを含む
新しい組合せで比較する。数値は正規化後の一致と厳密な一致を別に数える。
単純なコピーが改善しても、自然言語のパターンから正規表現を作るケースを悪化させたら報告する。
入力長は短くなる可能性があるが、速度は別の測定で確かめる。

### H03: 段階に合った少数の正解例を示すと、指示だけより安定する

**文献。** [Schall・de Melo（RANLP 2025）](https://aclanthology.org/2025.ranlp-1.124/)は、
4–8Bのモデルで制約付き生成を調べ、形式に合った指示と例示の効果を報告している。
[Minほか（EMNLP 2022）](https://arxiv.org/abs/2202.12837)も、分類・選択問題の例示について、
入力分布、ラベル集合、書式の寄与を調べている。これらは本実装への適用を考える根拠であり、
0.6Bでの改善や最適な例数を示すものではない。

**仮説と比較。** 同じ指示で0例・1例・3例を比べる。名前選択への例示と引数生成への例示は別々に試す。
各例には、その例で使う関数定義と依頼文、正解を含める。
名前選択の正解は名前だけ、引数生成の正解は現在の`prompt/name/parameters`形式に合わせる。
評価集合の問題・答えは例に入れない。3例は1例の集合を含み、追加する例を事前に固定する。

引数生成の例は、たとえば次のような短い形にする。これは候補の形を示す架空の関数である。

```text
Example function: save_reading(value: number). Store the supplied reading.
Example request: "Save the reading -7.25."
Example response:
{"prompt":"Save the reading -7.25.","name":"save_reading","parameters":{"value":-7.25}}
```

**判定。** 例と異なる関数名・数値・言い回しでも改善するかを測る。
例の答えや名前の模倣、他の型の悪化も数える。例を増やしても完全正答が増えなければ、短い候補を優先する。
このSDKでは入力増加が各生成ステップの計算に影響するため、例数を無制限に増やさない。
Minほかのランダムラベルに関する結果を、誤った引数例を入れる理由には使わない。

### H04: 関数一覧の区切りと回答直前の書式で、名前選択が変わる

**文献。** [Sclarほか（ICLR 2024）](https://arxiv.org/abs/2310.11324)は、
意味を保ったプロンプトの書式変更でもfew-shotの結果が変わり、良い書式がモデル間で
そのまま移らないことを報告している。

**観測と仮説。** 既存の5件では、関数一覧や回答接頭辞の変更によって名前選択が変わった。
この結果は候補を作る材料であり、未知入力への優位性を示さない。
一覧を項目ごとに区切ると、説明と名前の対応を選びやすくなると仮定する。

過去の接頭辞比較には、`Selected function: `に続く制約前の第1候補が空白付きの` set`で、
採用結果が`heartbeat`だった例もある。名前の木は単独の名前をencodeした経路を使うため、
先頭空白付きの別トークンは許可されない。対象は変更セットのdisableケースで、
`allowed_mass=0.000520495`だった。現在の`Function name:\n`では同じケースで
`set_enabled`を選べている。元のログは開発キャッシュの
`.cache/implementation/name-prefix-variants.log`にある。
この観測だけでは、接頭辞の文言と末尾空白のどちらの効果かは分からない。

**比較。** 現在の1行形式と、下の項目形式を比べる。関数の順序、名前、説明、引数情報、
依頼文、指示、`Function name:\n`は同じにする。その後、採用候補の一覧形式を固定して、
回答接頭辞の文言を`Function name:`にそろえ、末尾の改行・空白・区切りなしを別実験で比べる。

```text
Name: <exact function name>
Description: <unchanged description>
Arguments: <unchanged names and types>
```

**判定。** 名前選択の正答件数と、正答から誤答・誤答から正答へ変わったケースを並べる。
特定の関数位置や既知の1件だけで改善するなら、汎用的な改善として扱わない。
書式ごとの入力トークン数も記録する。

### H05: 引数生成から戻り値の型を省くと、不要な情報が減る

**仮説。** `returns`を提示しない方が入力引数に集中できる。
根拠は処理の責務から立てた推測であり、該当フィールドの削除効果を示す研究は今回確認していない。
型だけの`returns`では影響がない可能性もある。

**比較。** 引数生成に提示する関数JSONから`returns`だけを省く。
関数定義ファイル、入力検証、名前選択、生成するJSON、他の説明は固定する。
フィールドを省いたことで説明文や型の情報まで変えない。

**判定。** 入力と結果を混同しやすい関数と、それ以外の関数の両方で引数精度を比べる。
精度が同じなら、トークン削減量を記録して時間の候補に残す。
パラメーターごとの説明を新設する案は、現在の入力スキーマを変えるため、この比較には含めない。

### H06: JSONの指示を短くしても、構造を保って意味の精度を維持できる

**仮説。** コードが強制する構造の説明を短くすると、値抽出に必要な指示の割合を増やせる。
一方、制約付き生成にも出力形式を説明する必要があるというH03の文献結果は、削りすぎに対する反証候補になる。

**比較。** 現在の`Return only a JSON object with prompt, name, parameters.`と
`Use JSON numbers, strings, true/false.`を、次の1文に置き換える。他の文は固定する。

```text
Continue the provided function-call JSON by filling its parameters.
```

**判定。** 引数精度、完了率、生成トークン数を比較する。
`allowed_mass`が改善しても、意味の正答が増えなければ精度改善と判断しない。
マスクや強制するJSON構造は全候補で維持する。形式をプロンプトだけに任せる実験ではない。

### H07: 例・関数・依頼文の位置による偏りがある

**文献。** [Luほか（ACL 2022）](https://aclanthology.org/2022.acl-long.556/)は例示の順序依存を、
[Liuほか（Lost in the Middle）](https://arxiv.org/abs/2307.03172)は長い文脈での関連情報の位置依存を報告している。
例の順序の結果を関数一覧に、長文の結果を短いプロンプトに適用する部分は、新しい仮説である。

**比較。** 次の比較は混ぜず、それぞれ内容を固定して行う。

- H07a: H03の同じ3例を、事前に決めた複数の順序で並べる。
- H07b: 同じ関数一覧を並べ替え、正解関数が先頭・中央・末尾に来る条件を作る。
- H07c: 関数定義の前後で依頼文の位置を入れ替える。現在は依頼文が後なので、前に移す条件と比べる。

**判定。** 平均正答率に加え、並び替えだけで答えが変わる件数を測る。
常に正解を先頭に置いた評価はできないため、複数の順序に対して安定する候補を探す。
H07cでもassistant側のコピー済み`prompt`欄は固定する。
そのコピー自体を省く案は、骨組み・生成後の再構成を変える別の部品実験になる。

### H08: Qwenの標準的なツール呼び出し形式に合わせると改善する

**公式資料。** [Qwenのfunction callingガイド](https://qwen.readthedocs.io/en/stable/framework/function_call.html)は
Qwen3にHermes形式を推奨している。
[使用中のリビジョンのテンプレート](https://huggingface.co/Qwen/Qwen3-0.6B/blob/c1899de289a04d12100db370d81485cdf75e47ca/tokenizer_config.json)にも、
`<tools>`内の定義と、`<tool_call>`内の`name/arguments`という形式がある。

**仮説。** 学習時に近い可能性のある入出力形式なら、独自の出力形式より意味を選びやすい。
公式の推奨は根拠になるが、この2段階方式との優劣は未確認である。

**比較候補。** まず定義を`<tools>`で囲む入力側の手掛かりだけを比べる候補を作れる。
ただし、名前だけを答えさせる現在の方式のままなら、これは完全なHermes形式ではない。
標準の`name/arguments`を生成し、提出用の`prompt/name/parameters`へ組み直す比較は、
プロンプトだけでなく内部の骨組み・制約・再構成を変える。別の設計・承認を要する候補として残す。
最終出力の契約は両条件で同じにする。

**判定。** 名前・引数・全体の精度と構造適合を測る。完全な方式変更で改善した場合、
改善を「タグを足した効果」と限定して説明しない。優先度は、現在の方式での短い比較より後に置く。

### H09: 非推論モードでは、入力全体の反復が助けになる

**文献。** [Leviathanほか（2025、プレプリント）](https://arxiv.org/html/2512.14982v1)は、
7種類のAPIモデルで、推論を求めないときの入力反復による改善を報告している。
Qwen3-0.6Bや本実装の制約付き生成での検証ではない。

**比較。** system指示、出力接頭辞、制約を固定し、userメッセージの内容全体
（関数定義と依頼文）を1回提示する条件と、同じメッセージ内で2回続ける条件を比べる。
名前選択・引数生成は別に試す。依頼文だけを反復する条件は、論文の入力全体の反復と区別する。

**判定。** 完全正答と入力トークン数を比べる。既に引数生成にはコピー済みの依頼文もあるため、
何を何回提示したかを保存する。このSDKは各logits呼び出しで全入力を渡し直し、KVキャッシュを再利用しない。
APIのprefillを前提とした論文中の速度の結果は適用できない。
入力増加の費用があるため、優先度は低く、時間は単独実行で別に測る。

## 「順を追って考えよ」とサンプリングを初回比較に入れない理由

現在の名前・値の生成には自由な説明文を出せる場所がない。
`Think step by step`を追加しても、その説明トークンは制約で選べない。
別の推論段階を設けるなら、プロンプトだけの比較から分けて設計する必要がある。
[Tamほか（2024）](https://arxiv.org/abs/2408.02442)は形式制約下での推論性能低下を報告しており、
Schall・de Meloの実験でもJSONに推論欄を加えるだけで改善するとは限らなかった。
これらから、推論文の追加を初回の既定案にはしない。

[Qwen3-0.6Bのモデルカード](https://huggingface.co/Qwen/Qwen3-0.6B)は推論を無効にする
`enable_thinking=False`を用意している。現在の空のthinkブロックは、そのテンプレートに対応する。
同カードのgreedyを避ける注意はthinking modeの項にあり、non-thinkingにも同じ禁止があるとは読まない。
non-thinkingにはサンプリング設定の推奨もあるが、初回は承認済みのgreedyを固定して文面の効果を測る。
選択方式の比較は、その後の部品実験にできる。

## 後続の並列実験の進め方

### 評価集合と正解の固定

入力の関数定義と依頼文を固定し、モデルへ渡すプロンプト候補を比較する。
次の3段階を別々に評価する。

1. 名前選択だけを評価する。
2. 正解の関数を指定して引数生成だけを評価する。名前の誤選択の影響を取り除く診断用の評価である。
3. 通常の処理全体を評価する。

既存サンプルは回帰確認に使い、候補を作る開発集合と、最後まで使わない評価集合を別に用意する。
同じ文章の数値だけを変えて両集合へ分配すると似た問題への調整になるため、
関数の組合せ・依頼の文型ごと分ける。曖昧な依頼は正解を先に確認し、採点途中で都合よく変えない。
当面は英語の指示を対象にし、文字列値に含まれる非ASCII文字の保持は別の項目として確認する。

### 記録する指標

| 指標 | 数え方・目的 |
| --- | --- |
| 完了率・エラー | 入力総数を分母とし、上限到達やSDK失敗も残す。成功例だけで採点しない |
| JSON・スキーマ適合 | 保存できた出力の適合率と、適合した出力件数/入力総数の両方 |
| 名前の正答 | 名前が一致した件数/入力総数。関数別の取り違えも記録 |
| 引数の正答 | 正解関数を与えた場合と通常処理を分け、number/string/boolean別にも記録 |
| 完全正答 | 関数名と全引数が正しい件数/入力総数。候補選択の主指標 |
| 値の詳細 | 負号、文字列の端の空白、引用符、エスケープなど、何が変わったか |
| 生成・診断 | 段階別の入力・生成トークン数、logits呼び出し回数、raw_top、採用トークン、allowed_mass、gap |

正規表現は表記一致に加え、別に用意した複数の入力で要求された動作になるか検査する。
有限の検査で一般的な意味の同値を証明したとは扱わない。
長い小数などでは、生成した表記とfloat正規化後の出力を分ける。
承認済みのfloat変換で失う精度を、プロンプト改善で直せる誤りには数えない。

`allowed_mass`は、そのステップで許可されたトークンの確率の合計である。
名前が正しい確率ではなく、`gap`も正答を保証しない。
既存の誤選択には、制約前の第1候補自体が許可された誤った関数だった例がある。
警告の数値と正解の対応を調べ、誤答を見逃す場合と正答に警告する場合を両方記録する。

greedyで同一入力を反復するのは再現性の検査であり、独立した新しい問題が増えたとは数えない。
候補間では同じ問題同士を比較し、件数、分母、正誤が入れ替わった問題を示す。

### エージェントに渡す仕事

[ProTeGi（EMNLP 2023）](https://aclanthology.org/2023.emnlp-main.494/)は、誤答から自然言語の批評を作り、
改稿候補を評価して探索する方法を提案している。
[OPRO（ICLR 2024）](https://arxiv.org/abs/2309.03409)は、既存候補と評価値の履歴から次の候補を生成する。
両者は後続の探索手順の参考になり、論文のパッケージを導入する必要はない。

並列作業は、次の役割に分ける案とする。

- 候補を提案するエージェント: 担当する仮説と開発集合の誤答から、変更点と予測を書く。
- 実行するエージェント: 固定した候補を実行し、生の出力と診断を候補別に保存する。
- 採点・比較するエージェント: 事前の正解を使って採点する。提案者の説明を正解判定の根拠にしない。

各候補には、親候補、仮説ID、変更した文、プロンプト全文とハッシュ、コードのSHA、モデルリビジョン、
入力集合のハッシュ、dtype、選択方式、上限、スレッド数、エラーを残す。
複数エージェントが共有の`src/prompt.py`を同時に書き換える方式は避け、
固定したコードに候補ごとの設定を渡し、出力先も分ける。ブランチを候補ごとに増やす必要はない。

現在の測定ツールは入力fixtureと反復数には対応しているが、候補設定の指定、正解関数を固定した評価、
上記診断の集計は未実装である。実験を依頼された段階で、この準備を設計・確認する。
今回はツールを改修していない。

### 最初の比較と時間測定

最初は基準に対してH01・H02・H03の引数生成への1例・H04の項目形式を
それぞれ単独で変えた、計5条件を推奨する。
一度に全部を組み合わせず、改善が見えた候補の組合せを次に確認する。
H05以降は、その誤答と費用を見て追加する。
開発集合で候補を選び、未使用の評価集合は最終確認に回す。
最終確認の結果を見て改稿したら、その集合も以後は開発用になる。

精度の試行は並列でよい。並列実行中の経過時間から速度の優劣を結論づけない。
時間は、精度測定の自分たちのモデルプロセスを止めてから、選んだ候補を単独で測る。
起動から終了まで、モデルキャッシュ、ハードウェア、スレッド数、完了件数を記録する。
長大文字列は既存の測定で高負荷・未完了になったため、初回の文面比較と分け、
実行範囲と中止条件を先に定める。測定方針は[ADR-0010](../design/adr/0010-measurement-policy.md)に従う。
