# ADR-0001: 関数名の選び方

状態: 決定(ユーザー、2026-11-08)。精度は要検証。

## 背景
- 【明文】関数の選択は LLM が実行時に行う。ヒューリスティクスは不可(IV.3.1)。
- 【明文】無効なトークンの logits を負の無限大にして、残りから選ぶ(V.3.3)。
- 【測定】SDK の `get_logits_from_input_ids` は、呼ぶたびに入力列全体をモデルに流し直す。返るのは最後の位置の
  logits だけで、KV キャッシュは使わない(`llm_sdk/llm_sdk/__init__.py` のソース)。時間は
  「logits の呼び出し回数 × そのときの入力長」でほぼ決まる。
- 関数名は複数のトークンに分かれる。ある名前が別の名前の接頭辞になりうる(`fn_add` と `fn_add_numbers`)。

## 選択肢
- a. 名前の木: 各関数名を `encode` でトークン列にして木を作る。次に許すのは、どれかの名前の続きだけにする。
  貪欲に選ぶ。名前が1つに決まった後は、残りのトークンを強制する。
- b. 候補ごとの確率: 候補の名前それぞれの確率を計算して比べる。トークンの境界に強いが、
  候補ごとにトークン数ぶん logits を呼ぶ。
- c. 関数を専用トークンにする(Octopus v2): 学習が要る。対象外。

## 決定
**a**。

- 【設計判断】名前の終わりを示す記号(閉じ引用符)も木に入れる。接頭辞の衝突を解く。
- 【設計判断】関数定義が空、名前が重複、名前が空、のときは起動時にエラーにする。
- 【解釈】制約付きデコードとして防御できる。候補が1つしかない位置では、マスク後の最大値は、モデルの出力に
  かかわらずそのトークンになる。強制トークンはマスクの結果と同一で、logits の計算を省くだけで、出力は変わらない
  (貪欲選択の場合)。

## 精度についての根拠と限界
- 【測定】PoC の final(30件)と extra(90件)で、C の関数選択は100%、B は70%。条件は揃っていない。
- 限界: PoC の C の実装コードはリポジトリに無く、名前の木を使っていたか不明。関数は5つ前後だった。
  レビューでは関数セットが変わる。
- 検証の方針: 関数の数と種類を変えたテストで、関数選択の精度を単独で測る。

## 見直しの条件
- 関数選択の精度が目標(90%)を下回る。または、名前の分岐が遅い関数どうしで誤る。
- その場合の候補: 候補の並び順の入れ替え(順序の偏り)、案bへの切り替え。
