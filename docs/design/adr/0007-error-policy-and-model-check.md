# ADR-0007: エラー方針とモデルの確認

状態: 決定(ユーザー、2026-11-08)。モデルのファイルの確認は、2026-11-09 に取りやめた(下の「更新」)。

## 背景
- 【明文】すべてのエラーを適切に処理し、明確なメッセージを出す。予期しないクラッシュは不可(IV.3.1)。
  未処理の例外でクラッシュしたら「動作しない」扱い(IV.1)。
- 【解釈】SDK は、モデルの取得を構築時に暗黙で行う。取得するリビジョンを指定する引数はない。
- 【解釈】プロジェクトのコードは `huggingface_hub` を直接 import できない(`docs/subject-v1.7.md` 第1章の解釈)。

## 決定
- 【設計判断】入力は、モデルを動かす前に検証し、エラーなら終了する。対象は、引数、ファイルの有無、JSON の形式、
  関数定義(空、重複、未対応の型)、ネットワークとキャッシュ。
- 【設計判断】1件の処理が失敗したときは、その件を飛ばし、標準エラーに理由を出し、他の件は続け、最後に
  終了コードを非0にする。結果は1件ずつ原子的に保存する。
- 【設計判断】ただし、1件の失敗が起きない設計を目指す。エラーが出ること自体が、Subject 違反になりうる
  (クラッシュ扱い)ため。ここで述べた処理は、最後の安全策とする。
- 【設計判断】モデルの読み込みと推論の例外は、すべて捕捉し、原因が分かる明確なメッセージで、安全に処理する
  (握りつぶさない。非0で終了する)。

### モデルのファイルの確認(2026-11-09 に取りやめ。下の「更新」を参照)
- 【設計判断】完全性は、**実行時に** sha256 で確認する。比べるハッシュは3つ。
  - lock: ロックファイルに保存した、固定したバージョンのハッシュ。**ロックファイルは Git で管理する**。
    理由: 不用意なバージョン差が起因の問題を減らすため。
  - latest: 上流の最新バージョンのハッシュ。
  - cache: 手元のキャッシュにあるファイルのハッシュ。
- 【設計判断】判定:
  - cache が lock と一致し、latest も lock と一致する: 問題なし。
  - cache が lock と一致し、latest が違う: **警告**(上流に新しい版がある)。続行する。
  - cache が latest と一致し、lock と違う: **警告**(ロックと違うバージョンを使っている)。続行する。
  - cache が lock とも latest とも一致しない: **エラー**(破損)。入れ直す手順を表示して終了する。
- 【設計判断】取得時は最新版を使う(SDK の挙動)。出版元を信頼し、評価中は変わらないと考える。

## 要検証(取りやめ。下の「更新」を参照)
- latest のハッシュをどう得るか。上流が公開する情報(LFS ファイルは sha256)を、標準ライブラリの通信で
  取る案。`huggingface_hub` は使えない解釈のため。標準ライブラリの利用が、Subject の「使ってよいパッケージ」
  と衝突しないかは未確認。
- オフラインで latest を取れないとき: cache が lock と違うと、破損かバージョン差か区別できない。扱いは未決
  (案: 警告にとどめる)。
- cache のハッシュの確認: 検証済み(2026-11-08。huggingface-hub 2.4.0 のキャッシュ、Qwen3-0.6B の4ファイル)。
  大きなファイル(`model.safetensors`、`tokenizer.json`)の blob 名は、中身の sha256 と一致した。
  小さなファイル(`vocab.json`、`merges.txt`)の blob 名は、git の blob ハッシュ(SHA-1)と一致した。
  キャッシュの配置は huggingface-hub のバージョンに依存する。`uv.lock` で固定したバージョンでの結果。
  別のバージョンでは、配置が違う可能性がある。
- 対象とするファイル(重み、トークナイザ、設定のうち、どれか)。

## 見直しの条件
- 上の方法が使えないと分かったとき。
- 警告が頻発して、実害の無いバージョン差で運用が混乱するとき。

## 更新(2026-11-09)
- 【設計判断】(ユーザー、2026-11-09)モデルのファイルの確認(lock、latest、cache の 3 つのハッシュと警告)は
  **やめる**。例外処理だけにする(案 A)。今は余計な実装を入れない。ロックファイルも要らなくなった。
- 理由: Subject が求めるのは、例外を適切に処理し、明確なメッセージを出し、クラッシュさせないこと(IV.1、IV.3.1)。
  モデルのファイルの完全性は求めていない(`docs/subject-v1.7.md` の要約で確認。原文では見ていない)。
  上の「要検証」の項目(latest のハッシュの取得、オフライン時の扱い、標準ライブラリの通信と Subject の関係)は、
  すべて latest に由来する。
- 残る決定: 上の「モデルの読み込みと推論の例外は、すべて捕捉し、原因が分かる明確なメッセージで、安全に処理する
  (握りつぶさない。非 0 で終了する)」。
- 検出できないもの: 読み込めるが壊れているモデル。壊れたファイルを SDK が例外にするかは、試していない(推論)。
- 見直しの条件: 「壊れているが動く」モデルが、実際に問題になったとき。候補は、キャッシュと lock のハッシュだけを比べる案
  (ネットワーク不要)と、固定のプロンプトで 1 回推論して先頭トークンを確かめる案(未測定)。
