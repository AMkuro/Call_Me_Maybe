## 現在の問題と根拠

| 実装で確認した事実 | 変更への影響 |
| --- | --- |
| `pipeline._show_choice` が列幅16・小数3桁・採用記号・masked表記を決める | 表示変更が生成モジュールの修正になる |
| `Run.say(label, text)` と `Dashboard.report` が文字列を受け取る | 未知のイベントも受理し、入力開始・完了・失敗と表示フィールドの区別を型で確認できない |
| `Dashboard.fields` が表示値と集計に必要な入力番号・関数名の両方を保持する | 表示フィールドの変更が要約や状態遷移に影響する |
| `_start` 後に `run.report = dashboard.report` を代入する | モデル準備と観測先の寿命が混在し、呼び出し時点で依存先が確定しない |
| リダイレクトでも通知先があり、全トークンでexp・sort・top-10・表示用decodeを行う | 警告と要約しか出さない実行に不要な計算がある |
| `TokenChoice` はfrozenだがlistフィールドが可変で、strict・extra拒否・整合性検証がない | 受け手が履歴を書き換えられ、不正な観測値を構築できる |
| 通知関数の例外がdecoderから伝播する | 診断処理の失敗で正常な生成を失敗扱いにし得る |

候補表示と要約の仕様はADR-0021のユーザー決定である。列幅・reportの形・Runへの集約は
実装方法であり、今回はその再評価を要求されている。Modelを抽象Protocolにしないことと、
SDKハンドルだけのクラスにPydanticを足さないことはADR-0011の既存決定として保つ。

## 選択肢と推奨

1. 整形関数だけdisplayへ移す。差分は小さいが、文字列契約・状態管理・後付け注入が残る。
2. **型付き観測契約、明示的な表示状態、通知先と実行依存の分離（推奨）**。
   生成の関数構成を保ちながら、問題がある境界を変更できる。イベントと状態の検証が増える。
3. GenerationSessionサービスへ生成を集約する。関連操作は見渡せるが、生成中の可変状態は
   現在ローカル変数で完結しており、クラスへ移す理由が弱い。今回の推奨に含めない。

決定: **未決。2を推奨するが、人間の設計承認を待つ。**

## 提案する責務と依存方向

```text
main ──→ pipeline ──→ decoder ──→ choose_token
  │          │            │
  │          └──→ observation ←──┘
  └──→ display ──→ observation
```

`observation.py` は型付きデータと通知の契約だけを持つ。端末・SDKをimportしない。
decoderは選択と同じlogitsから観測データを作り、pipelineは段階・関数・引数の文脈を通知する。
pipelineはdisplayをimportせず、表示用decode・候補表・警告文の整形を持たない。
mainが実行依存とDashboardを組み立て、起動・全件処理・保存・終了を所有する。

### 通知の契約

文字列labelと自由なtextの組を廃止する。少数のPydanticモデルによる判別可能なunionを用いる。
開始・終了・段階変更・選択関数・引数開始・トークン選択を区別する。
イベント種別ごとにクラスを無制限に増やさず、完了と失敗は終了イベントの結果で区別する。
トークンイベントは既存のTokenChoiceを保持し、診断値の別モデルを重複して作らない。
TokenChoiceの定義はobservationへ移し、decoderからもimportして既存利用箇所へ再公開する。
observationからdecoderはimportしない。これによりイベントとの循環importを防ぐ。
引数名と型は別々の値として渡し、`name (type)`への整形は表示側で行う。

通知先は単一のCallableを使う。複数購読者・イベントバス・Observer階層・モデルProtocolは不要。
一実行の小さなObservationクラスが、そのCallableと現在の診断要求
`none`・`warnings`・`full`を保持する。Pydantic dataclassで構築時に検証し、
mainがDashboardと同じスコープで生成して処理関数へ渡す。
これは選択規則ではなく計算要求であり、decoderはTTYを参照しない。
各トークンでObservationの現在の要求を確認する。Dashboardの受信関数は継続可能かをboolで返し、
stderr故障ならFalseとする。ObservationはFalseまたは通知例外で要求をnoneへ変更する。
観測停止という可変状態と、通知する関連操作を一緒に管理するためのクラスであり、継承は設けない。
受信済みPydanticインスタンスは再検証せず、外部由来の値や新規イベントの構築境界で検証する。

観測の例外は診断計算・イベント構築・通知を含む範囲で捕捉し、Observationを停止する。
生成・保存・最終値decodeの例外は従来どおり扱う。トークン選択後に観測範囲へ入り、
観測失敗後も同じ採用IDを生成列に保持する。
`KeyboardInterrupt`・`SystemExit`は捕捉しない。観測失敗後は観測を止め、生成は続ける。
正常な生成を破棄しないための隔離であり、不正イベントを黙って有効化するものではない。
イベント自体の不正構築は単体テストで直接検出する。

### Runとライフサイクル

Runはモデル・語彙・関数辞書・名前の木という起動時に確定する依存だけを保持する。
report・sayを取り除き、通知先は処理を呼ぶときに別引数で渡す。
mainはDashboard生成後に通知先を渡すため、後からRunを書き換えない。
Runは生成途中のids・text・slotを保持しない。名前・値の生成は関数のままにする。

Runは通常のdataclassから、Pydantic dataclassへ変更する案を推奨する。
Modelの型注釈はInstanceOfで具体的なラッパーであることだけを確認する。
これでSDK内部の検証ができたとは扱わず、`arbitrary_types_allowed=True`は使わない。
語彙・関数・木の検証は起動時だけで、モデルの再ロードや各トークンでの辞書検証はしない。
大きい語彙のコピー費用と既存オブジェクトの同一性は検証する。frozenは浅い不変性であり、
共有辞書は構築後に変更しない契約とする。コピーやimmutable辞書の新設は推奨しない。

### Dashboardの状態と整形

Dashboardは一実行のstderr資源・計時・画面復帰を管理するサービスとして残す。
現在のプロンプトと集計はPydanticの状態モデルで検証し、表示用辞書から独立させる。
正のtotalはPydanticで構築時に検証する。状態はイベント単位で更新し、画面描画時に再検証しない。

- 開始前はactiveなし。開始すると入力番号・prompt・開始時刻を確定する。
- 終了はactiveな入力に一度だけ適用する。終了イベントが成功か失敗かを指定する。
- 成功時の名前は終了イベントに含め、直前の表示フィールドから推測しない。
- 次の入力開始時に段階・関数・引数・値・警告・候補を一緒に初期化する。
- `done + failed <= total`。中断件数はtotalとの差から求め、成功・失敗に加算しない。
- 重複終了・開始前の終了・範囲外の番号などは状態更新前に拒否し、集計を壊さない。

候補表の整形とトークン表記はdisplay内の関数にする。render_progressは決定的な純粋関数のまま保つ。
SDK decodeが必要な名前の途中経過や特殊トークンの表記は表示アダプターが行う。
displayにはModel全体ではなくdecodeの関数と語彙だけを渡す。decodeの失敗は従来の取得不能表記へ変換する。
制御文字のエスケープ、CJKの幅切り詰め、更新間隔、終了後要約を維持する。
閉じたstreamのValueErrorとOSErrorは表示失敗として扱う。端末復帰はcontext managerで試行する。

### 診断計算の段階

| 要求 | 名前の分岐 | 引数の分岐 | 強制位置 |
| --- | --- | --- | --- |
| none | 選択だけ | 選択だけ | 推論なし |
| warnings（リダイレクト） | 制約前の第1候補と採用IDを比較、警告時だけ表記 | 観測なし | 推論・候補計算なし |
| full（端末） | 現行のtop-10・確率・gap・途中経過 | 同左 | 強制であることと途中経過のみ |

warningsでも既存の名前選択警告は残す。生logit最大の同点時は小さいIDを優先する。
現行top-10のargpartitionには境界同点の選択保証がないため、この規則が現行の全ケースと
一致するとは断定しない。警告用のargmaxをfullでも共用し、表示モードによる警告判定の差を防ぐ。
選択IDは変わらないが、境界同点での警告判定を明確にする実装詳細の変更として承認対象に含める。
選択に使うchoose_tokenは変更しない。診断は選択済みlogitsを読み、forwardを追加しない。
stderr故障後は診断を止める。端末サイズによる自動的な候補数変更は行わない。

### PydanticとSubjectの整合性

データにはBaseModel、RunにはPydantic dataclass、Dashboardには検証済み状態・設定を使う。
ObservationもPydantic dataclassを使い、診断段階とCallableの型を構築時に確認する。
Callableの内部動作はPydanticでは検証できず、呼び出し時の隔離とテストで確かめる。
構造化イベントとTokenChoiceはstrict・extra=forbid・frozenを基本とし、可変listをtupleにする。
stepは正、IDは非負、生成列長とstep・末尾tokenの一致、forcedと診断値の整合性を検証する。
allowed_massは有限な0～1、logitは有限とする。gapは既存に正の無限大があり得る
（許可候補の片方だけが有限な場合）ため、NaNと負値を拒否して正の無限大は保つ。
Pydantic dataclassとBaseModelは、状態更新操作や資源管理の代用にはしない。

Modelと例外はADR-0011の既存解釈に従い通常クラスを維持する。Modelは引数なしで公開SDKをロードし、
新しい検証対象の設定を持たない。Dashboardはtotalと状態の検証でPydanticを利用するため、
BaseModelの継承だけで見かけ上対応する案を採らない。
Subjectの「All classes」の評価者解釈は確認できず、Modelと例外を対象外とする既存解釈には評価上のリスクが残る。
本提案で厳密な適合を保証したとは記録しない。

## 変更単位と影響範囲

1. **表示分離**: displayに候補整形を移し、pipelineの文字列整形を外す。
   生の選択データを渡す最小の通知変更と表示側のdecode依存を同時に入れる必要がある。
2. **観測契約と状態**: 型付きイベントへ置換し、TokenChoice検証、状態モデル、診断段階、
   観測失敗の隔離を導入する。mainの開始・成功・失敗通知も同時に変える。
3. **Runの整理**: 通知先を別引数にし、Pydantic dataclass化と後付け代入の削除を行う。
   関数をサービスへ移すだけのOOP化は行わない。

各単位をレビュー可能なローカルコミットとするが、承認された設計の実装は一括して進め、
最後に全チェックとレビューを行う。呼び出し変更はtest_application、test_skeleton_flow、
test_function_registry、test_terminal_progress、test_dashboard_candidatesへ届く。
decoder直接呼び出しの既存テストも更新対象。既存fixtureの内容・依存・CLI・SDKは変更不要。
実装後にarchitectureとADR-0014/0021の現行契約記述を合わせ、過去の測定結果は保存する。

## 承認対象と見直し条件

設計レビューで、観測停止の所有者が未定義であることとTokenChoiceの循環依存の可能性を指摘された。
上記のObservationによる停止状態の所有と、TokenChoiceの配置を追記して解消した。
レビューは設計の読解によるもので、実装の検証ではない。

承認を求めるのは、上記の責務境界・型付きCallable契約・診断3段階・Runの分離・
Pydantic利用方針である。生成アルゴリズムや表示仕様の変更は含まない。
状態を持つ生成処理が将来必要になった場合にサービス化を再検討する。
Pydanticの構築費用が実時間に影響する場合は検証境界を計測して見直す。
評価者が全通常クラスに検証を要求する場合は、既存ADR-0011を人間の判断で改訂する。
