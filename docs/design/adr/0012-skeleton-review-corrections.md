# ADR-0012: 値の終了、JSON の組み立て、結果の保存

状態: 修正方針はユーザー承認済み(2026-11-09)。5 点の修正案を提示し、「うん」と承認を得た。
具体的な引数・フィールドの追加は、以下の方針を実装するための詳細である。
空入力の扱いは2026-11-10にユーザーが変更を承認した。末尾の変更が元の方針5に優先する。

2026-11-10の値生成の設計更新: [ADR-0015](0015-value-records.md)では、値の終端を
引用符外のLFへ変更し、JSONのカンマ・括弧をすべてForcedへ戻す。
値を正規化してから最終JSONに入れ、生の生成ID列は同じ応答の文脈として継続する。
下記の方針1と`ValueSlot.terminator`は旧設計の記録で、コードはまだ旧方式。
保存・空入力・その他の修正方針は変更しない。

## 背景と要件

Subject v1.7 は、動的な定義に合う JSON、適切な例外処理、明確なエラー表示を求める
(`docs/subject-v1.7.md` 第 1、2、4 章)。ADR-0004 は number の float 化、ADR-0007 は
1 件ずつの原子的な保存と、失敗した件を飛ばす方針を定めている。

【測定】スケルトンの制御フローを固定データで確認した。数値 `12` は `1` で終了し、保存の
`OSError` は未捕捉になった。名前の引用符・バックスラッシュは JSON を壊し、検証後の
parameters は出力へ反映されず、結果 0 件では前回の出力が残った。実モデルの精度・時間は未測定。

## 選択肢とトレードオフ

- 値の終了: 数値として成立したら止める方法は、複数桁や小数を切り詰める。専用の終了記号を
  加える方法は JSON との変換が要る。後続の JSON 区切りを使えば、続きを出すか終了するかを
  モデルが選べ、生成済みのトークンをそのまま使える。
- 保存: 保存失敗をプロンプト失敗として続行すると、結果を保存できないまま推論が続く。
  保存失敗で終了すれば、それまでに保存した結果を保持して原因を報告できる。
- 結果 0 件: 前回のファイルを保持すると今回の結果と混同する。`[]` を保存すれば、今回の
  成功件数を表せる。入力検証・モデル起動が失敗した場合の保存方針は今回変更しない。

## 承認された修正方針

1. 値は、後続の区切り記号をモデルが選んでから終了する。数値として有効な接頭辞だけでは
   終了しない。区切りは骨組みで重複して出さない。
2. 保存の例外を捕捉し、原因を標準エラーへ出して非 0 で終了する。
3. 名前も `json.dumps` でエスケープし、骨組みの引用符と整合させる。
4. 動的モデルが検証・変換した parameters を戻り値に使う。
5. 空入力・全件失敗で処理を終えたときも `[]` を保存する。失敗した件があれば非 0 で終了する。

## コンポーネントとデータの流れ

- `ValueSlot.terminator` は `,` または `}`。最後の引数かどうかは `build_skeleton` が分かるため、
  スロットに持たせる。新しいクラスやモデルの抽象は追加しない。
- `allowed_value_tokens` と `is_value_complete` は終端を受け取る。値と終端を合わせた接頭辞だけを
  許可し、終端の後に余分な文字があるトークンを許さない。文字列・boolean も同じ契約に揃える。
- `generate_value` は終端を含むトークン列を返す。`generate_parameters` はそのまま追加する。
  骨組みは、スロットの後に同じ区切りを置かない。
- 例: 引数 a、b の場合、骨組みは `, "parameters": {"a": ` → a と `,` → ` "b": ` →
  b と `}` → `}`。引数なしは `, "parameters": {}}`。
- `pipeline` は prompt と名前をともに JSON 文字列として組み立てる。名前の閉じ引用符までを
  含めるため、`build_skeleton` の先頭は引用符を含まない。
- `validate_call` は検証結果の辞書を使い、新しい凍結済み `FunctionCall` を返す。
- `main` は成功ごとの保存と、結果 0 件の保存を同じ例外処理の対象にする。
  `writer` は原子的な保存を担当し、保存不能時は `OSError` を呼び出し元へ返す。

## 検証と見直し

末端の未実装関数は埋めず、契約と制御フローを直す。固定トークン・固定 logits と、未実装の
依存先の代替で回帰テストを行う。これは実モデルの精度・速度・JSON 適合率の証明ではない。
関数名の木の終端(ADR-0011)、文字列制約の細部、トークン上限は引き続き未決。

実モデルで区切りの結合トークンや境界に問題が出たら、この契約を見直す。

## 2026-11-10 の変更: 空の入力配列は入力不足

状態: ユーザー承認済み。「入力の空配列 [] は、モデル起動前に入力不足のエラーです」。

元の方針5では、結果0件の保存方針と、入力0件を正常として扱う判断を分けていなかった。
Subject の要約に空配列の許可を求める記述はなく、今回の扱いはユーザーが決めた入力契約である。

- 選択肢: 空配列を受理して `[]` を保存する方法と、入力不足として拒否する方法がある。
  前者は0件のバッチをそのまま処理できるが、処理対象を渡し忘れたことを検出しない。
  後者は利用者の入力不足を明示し、不要なモデル起動と既存の出力の変更を防ぐ。
- 決定: `load_prompts` が配列の件数を検証し、空なら StartupError にする。
  `main` はモデルを起動する前に原因を表示して終了コード1を返す。
  既存の出力は変更せず、出力がなければ新規作成もしない。
- 全件失敗は別の条件とする。1件以上の入力を処理して成功が0件だった場合は、
  元の方針に従って `[]` を保存し、終了コード1を返す。
- 検証: loader の直接テストと実際のファイルを使った main のテストで、
  明確なエラー、モデル未起動、既存出力の保持、出力の新規未作成を確認する。

0件のバッチを正常処理する要求が新たに生じた場合は、この入力契約と保存方針を改めて判断する。
