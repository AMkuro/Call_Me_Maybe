# ADR-0026: 固定JSON部分もトークン単位で確定する

- 状態: **採用（設計決定。実装・検証は未実施）**
- 日付: 2026-11-17
- 決定者: 開発者
- 背景: 独立監査 High #2。選択肢 B を採用。
- 要件正本: [REQ-025](https://github.com/AMkuro/pdf/blob/master/Call_Me_Maybe/requirements/decoding/constrained-decoding.adoc)
- 決定記録: [Issue #45 の後続判断](https://github.com/AMkuro/pdf/issues/45#issuecomment-6950812548)
- 関連: [REQ-030](https://github.com/AMkuro/pdf/blob/master/Call_Me_Maybe/requirements/decoding/schema-enforcement.adoc)、[Issue #13](https://github.com/AMkuro/pdf/issues/13)

## 背景と現行実装

Subject v1.7 L389 はLLM生成を token-by-token と説明し、L397–408 は次トークンの選択前にJSON構文・関数定義スキーマを制約する方式を説明する。L245は制約付きデコーディングを必須とする。

現在の `src/pipeline.py` は、関数名を `select_name`、引数値を `generate_value` でトークンごとに選び、`select_next_token` で許可候補を制限している。一方、`generate_parameters` はJSONの先頭を文字列で作り、`build_skeleton` が返す `Forced.text` を文字列連結し、その断片を `encode()` したID列を一括で文脈へ追加する。これは**現行実装の記述**であり、今回の追加決定の実装を完了したことは意味しない。

## 決定：選択肢B

出力JSONの固定部分（構造、キー、句読点、入力からコピーする `prompt`、選択済みの `name` など）についても、確定するトークンIDを**1個ずつ**出力生成状態へ反映する。引数などモデルが選択する部分は、従来どおり選択前にJSON構文とスキーマの制約を適用する。

1. 固定部分は決定的に確定してよい。許可候補が1つだけのステップでは、モデルのlogits取得・推論を省略できる。
2. どのステップでも、次のモデル選択で使う文脈は、それまでに確定した出力トークン列を正しく反映する。
3. すべての固定文字列をLLM自身に予測させる義務はない。生成中に逐次JSONファイルへ書き込む義務もない。
4. 無効logitsを `-inf` に設定する特定方式は引き続き必須ではない（Issue #13）。ただし可変部分の候補は、選択前に制約しなければならない。
5. SDKのprivate APIを使わず、提供SDKを改変しない。実装を `src/` の責務として扱う。

この決定は、課題のSubjectから導かれる生成条件を踏まえた**開発者の追加設計条件**であり、Subjectが全ての固定構文トークンでLLMをforwardするよう命じたと主張するものではない。

## 実装時に満たす不変条件

- モデルの次トークン選択に渡す `input_ids` には、関連する確定済み出力トークンの全履歴が、正しい順序で反映される。
- 固定部分のID列をまとめてトークン化することは可能だが、**確定状態へ反映する処理の粒度**は1トークンとする。各トークンでモデル推論を行う必要はない。
- `encode(A) + encode(B) == encode(A + B)` が一般に成立するとは仮定しない。テキストとトークン列の境界における意味的な一致を検証する。
- SDKの `decode()` が特殊トークンを省略するなど、出力とトークン列の単純な往復一致を壊す場合を考慮する。不一致を黙って成功扱いにしない。
- 関数名選択の独立した終端（EOSを含む経路）と、最終的なJSONレコード中の `name` の表現を混同しない。
- 完成したJSONは `prompt`・`name`・`parameters` の構造、入力文面の保持、選択した関数定義との一致を満たす。

これらの不変条件を満たすための具体的なデータ型や関数の分割は、このADRでは固定しない。既存の責務分離をできるだけ維持した実装案を比較し、差分とテストを確認してから採用する。

## 想定される変更箇所

- `src/pipeline.py`: 固定部分・可変部分を通じた生成状態の統一と1トークンずつの確定。現行の文字列組み立てとトークンID列の同期を検証する。
- `src/skeleton.py`: 固定部分の表現・消費方法がトークン単位の状態に適合しているか確認する。固定文字列を表す責務自体は維持可能。
- `src/decoder.py`: 一意候補では推論を省略できる現在の意味論を維持する。不要な抽象化や全ステップforwardを追加しない。
- `tests/`: 固定／可変の境界と文脈の不変条件を、SDK形状のモックと必要な実トークナイザー試験で検証する。

既存実装の編集、SDKの復元、精度測定、提出物の変更は**本ADRの作成時には実施しない**。

## 検証計画

1. 固定部分が複数トークンの場合でも、確定状態が1トークンずつ更新される。
2. 固定部分の直後に引数値を生成するとき、モデルに渡す文脈に正しい固定部分トークンが含まれる。候補が1つの場合はforwardが省略される。
3. 区切り記号を含む値、引数0個・複数個、特殊なキー名、エスケープ、非ASCII文字、トークン境界でマージの起きる文字列、特殊トークンに似た文字列をテストする。
4. トークンID列、復元した文字列、JSONとしての解析結果、Pydantic検証結果の整合性を確認する。
5. 終端しない値や候補なしの失敗を成功として扱わない。自由生成後のJSON修復だけで制約を代用しない。
6. 実モデル試験では、提供SDKの公開APIだけで動作すること、既存サンプルと変更関数セットの出力・精度・実行時間を確認する。性能の未測定事項を達成済みと記録しない。

## 非目標

- 既存SDKやモデル内部の改変
- すべての固定トークンでLLMのlogitsを取得すること
- token-by-tokenでのディスク書き込み
- 検証前の特定アルゴリズム・クラス階層の確定
- 本決定だけを根拠とする精度・速度・完全性の達成宣言
