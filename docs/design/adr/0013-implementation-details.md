# ADR-0013: 本実装の未決事項

状態: **ユーザー承認済み**(2026-11-10)。名前の終了トークンは暫定とし、
出力の障害になる場合は見直す。文字を壊さないバイト処理、暫定上限と理由付きのエラー、
調整用の数値付き警告を実装する。選択内容を TUI に表示する要望は ADR-0014 に記録した。
スケルトンは PR #43 で develop に統合した。

## 背景と要件

Subject v1.7 の動的な関数定義、JSON と型の制約を扱う。
Subject は入力言語を限定していないが、日本語プロンプトの精度目標を追加する提案ではない。
構成とデータの流れは [architecture.md](../../architecture.md) のままとし、以下の未決事項を埋める。
公開 SDK 以外でモデルを操作せず、SDK 自体も変更しない。

## 選択肢、提案と理由

1. **名前の終端**: モデルの応答終了トークンを使う案も成立する。前案の閉じ引用符は必須ではない。
   名前選択は引数生成と別の段階なので、名前だけを出して応答を終え、その後に引数生成へ移れる。
   現在の推奨案は `encode(name + "<|im_end|>")` を木に登録し、葉で元の関数名を取得する方法。
   ID は定数として埋め込まない。SDK の公開 encode を使う。
   閉じ引用符案は、JSON 文字列として名前を出す形式と合わせる点が利点。
   応答終了案は、名前だけを答える指示と自然に合わせられる点が利点。
   名前選択の生成列は、どちらの案でも引数生成に流用せず、選んだ名前を pipeline で JSON 化する。
   応答終了案をユーザーが暫定承認した。意味の正しさは実モデルで検証する。

   - `fn_add` と `fn_add_numbers`: `fn_add` の後で終了トークンか `_numbers` を選ぶ。
   - `fn_ad` のような未完成の名前: その位置の終了トークンは禁止する。
   - 唯一の候補に決まった後: 名前の残りと終了トークンを強制し、推論を省く。
   - 任意の場所で終了を許す実装にはしない。終了できるのは定義された名前の末尾だけ。
   - SDK の decode は終了トークンを表示しないため、表示文字列の末尾ではなくトークン ID の木で判定する。
2. **文字列と語彙**: 語彙を `dict[int, bytes]` として読む案を推奨する。
   Qwen の byte-level 語彙をバイト列に戻し、生成済みのバイト列と候補の全バイト列が
   JSON 値の接頭辞になるか検査する。UTF-8 の途中のトークンを許し、不正な UTF-8 を拒否する。
   単一トークンを個別に文字列へ decode する案は、分割された日本語が置換文字になるため採らない。
   完了した値は従来どおり SDK の decode を使う。文法は number/string/boolean の3種類だけ。
3. **生成上限**: ユーザー指示に従い、256トークンを暫定値として実装する。
   名前の上限を木の最長パスとする案は、終端の選択後に反映する。
   小数点以下16桁を最終的な仕様とする案は取り下げ、長い小数・大きな整数も測定して判断する。
   超過時はパラメーター名・型・上限・終端未到達を PromptError で伝える。
   正しく終了した値の切り詰め、途中で引用符を強制して短縮、別の数値表記への変換は行わない。
   有効な値の途中で文法が桁数上限に達する場合も、短い値へ誘導せず理由付きのエラーとする。
   測定ケースは tests/fixtures/generation_limit_cases.json。各3回、長い文字列、
   多数のエスケープ、17桁の小数、100桁と400桁の整数を含む。精度と時間は別に記録する。
4. **P1 の警告**: 未測定の確率閾値を置く案に代え、制約前の最大 logit が候補外なら警告する案を推奨する。
   名前選択の分岐でのみ判定し、候補内の最大 logit は通常どおり選ぶ。
   警告は「モデルの第1候補が許可された名前の続きではなかった」とし、「該当する関数なし」と断定しない。
   候補が1個の強制位置では推論しないため判定もしない。低信頼度の検出法としての有効性は未検証。
   ユーザーはプロンプト調整の目安になる警告を要求した。次の診断値を含める案とする。
   名前選択の段階、分岐位置、制約前の第1候補と採用した候補の ID・表示文字列、
   許可候補の確率の合計、許可候補1位と2位の logit 差。
   許可確率の合計は「モデルの全予測に対し、許可した続きが占める割合」で、関数の正答率ではない。
   比率と差は補助指標であり、単独では正誤も該当関数の有無も判定しない。
   警告例: `name_selection_constrained: step=3, allowed_mass=0.04, raw_top=..., selected=...`。
   1件との対応が分かるよう入力位置も付ける案。判定閾値は誤りの分析後に決める。

## 測定と限界

2026-11-10、配布 SDK の公開 encode/decode、Qwen3-0.6B のキャッシュ済み tokenizer を使用。
`fn_add`、`fn_add_numbers`、`日本語`、`say"hello`、`path\\name` の5例で、
閉じ引用符までの単独 encode と `{"name": "` に続けた encode が一致し、decode も一致した。
任意の名前すべての境界一致を証明する測定ではない。精度と時間はまだ測っていない。

追加の SDK 測定では、`encode("<|im_end|>") == [151645]`、
`encode("<|endoftext|>") == [151643]`。両方とも単独の decode は空文字になる。
`fn_add<|im_end|>` と `fn_add_numbers<|im_end|>` は名前の後ろに151645が付いた。
終了トークンを木に入れる方式の成立を確かめた測定であり、関数選択の精度測定ではない。

バイト分割は公開 SDK の decode でも再現した。ID2194と224はそれぞれ `�`、
連結すると「あ」。ID127と102もそれぞれ `�`、連結すると `é`。
Qwen は元から byte-level BPE で学習されているため、この提案でモデルの入力方式や重みを変えることはない。

Qwen の[公式発表](https://qwenlm.github.io/blog/qwen3/)は学習データの119言語・方言に日本語を含める。
[技術報告の表29](https://arxiv.org/html/2505.09388v1#A1.T29)では、0.6B の日本語 MMMLU は
thinking 45.1、non-thinking 37.9。関数選択・引数抽出とは異なる評価であり、
今回の90%達成可否を示す値ではない。日本語の学習量の内訳も、この調査では確認できていない。
推奨する対象範囲は英語の指示・関数定義で先に精度を測ること。日本語から英語への翻訳工程は追加しない。
バイト処理は文字化け防止として別に検討し、日本語の意味理解の精度を保証する機能とは扱わない。

固定 logits による上限の境界テストは、1・255・256トークンで完了、257・1024トークンまで
終端が出ない場合は256でエラー、の5条件を3回ずつ実行して通った。
これは終了条件とエラー表示の検証であり、実モデルで十分な上限を見極めた結果ではない。

## SDK の ID 変換と辞書の区別

ユーザーから、セットアップ時に外部ファイルの辞書を作れば `tolist()` を省けないかという案があった。
語彙の ID とバイト列の辞書は、既に起動時に SDK の公開語彙ファイルから一度読み込む。
一方、SDK の encode は入力ごとに新しい Tensor を返すため、それを decoder の ID リストに渡す
変換は別に必要になる。外部辞書を増やしても、この戻り値の型は変わらない。
入力全体の再利用や独自トークナイザーは別の選択肢だが、今回の要求には追加しない。
ラッパーは `tolist()` で得た ID リストをそのまま返し、再度の int 変換とリストのコピーを取り除いた。
その処理時間・メモリの寄与は未測定。`NAME_END` はユーザー指定で `EOS` に改名した。

## 見直しの条件

実モデルで、名前境界の誤選択、文字列の欠落、上限超過、警告の多発を観測した場合は、
精度測定と時間測定を分けて記録し、変更案をユーザーに示す。警告の確率閾値は実測後の判断に残す。
