# ADR-0015: 改行で区切る引数の中間表現と正規化

状態: ユーザーの方針を反映した将来の生成設計（2026-11-10）。LF・桁区切りは未実装。
ユーザーは改行区切りを暫定候補として認め、引数ごとの型制約、引用符内の改行の保持、
桁区切り付き数値をfloatへ正規化することを要求した。その後の精度保持要求により、
数値の受け渡しは[ADR-0017](0017-json-validation-and-precision.md)のint/検査済みfloatへ更新する。
LF方式を含む以下の具体的な文法・受け渡しは提案である。
設計書の本文・関連ADRにはこの方針を反映した。コード修正の依頼とは分けて扱う。

## 背景と要求

- Subject v1.7は、定義に一致するJSONと型、制約付き生成、正答率と時間の目標を求める。
  入力の関数セットは変わる。[ローカル要約](../../subject-v1.7.md)を参照する。
- 現方式では数値の`2,`が値の完了になる。依頼の`2,000,000`をモデルが同じ表記で出そうとすると、
  `2`で終了する可能性がある。`2.0`は型検証も通る。実モデルでこの依頼が誤るかは未測定。
- 【当初のユーザー要求】数値の生成表現を少し広げ、`2,000,000`もfloatに正規化して渡す。
  後続の精度保持要求では、丸めで値を変えないint/検査済みfloatへ変更する（ADR-0017）。
- 【ユーザー要求】文字列の引用符内の改行では次の引数へ進まない。引数の型ごとに出力を縛る。
- 【測定】キャッシュしたQwen3-0.6Bの語彙には、LFの1トークンがある。
  語彙の存在を確かめたもので、文脈中の最適な分割・選択精度・時間は測っていない。

## 選択肢

| 方式 | 利点 | 費用・制約 |
| --- | --- | --- |
| 現在のJSON区切り | 中間表現もJSONの断片で、生成IDをそのまま継続できる | 数値の桁区切りと引数区切りのカンマが重なる |
| 引数ごとにEOS | 各応答を単独の値として終えられる | 引数ごとの生成入力を設計する必要があり、forward費用の比較が必要 |
| 同じ応答内で、引用符外のLFを値終端にする | カンマを数値の桁区切りとして許せる。引数ごとの応答再開は不要 | 状態を持つ文法と、中間表現からJSONへの正規化が必要 |

LF方式を推奨する。数値の表記と終端を分け、既存の語彙と公開SDKだけで実装できるためである。
特殊トークンの別用途への転用は、下の理由から今回の推奨に含めない。

## 特殊トークンと配布SDK

トークンIDは、公開`encode`で取得し、logitsの候補として許可できる。
現実装も名前の終了に`<|im_end|>`を使う。SDKのlogits取得は1回のforwardであり、
EOSを自動検出して停止する生成APIではない。停止はdecoder側が判定する。
SDKの`decode`は`special=True`のトークンを省くので、終了をdecodeした文字の有無では判定しない。
SDKの`vocab.json`は基本語彙で、追加トークンの一覧はモデルの`tokenizer_config.json`にある。

| 登録された記号 | モデル側での用途 |
| --- | --- |
| `<\|im_start\|>` | system/user/assistant等のメッセージの開始 |
| `<\|im_end\|>` | 1メッセージの終了。現在の名前選択に使っているEOS |
| `<\|endoftext\|>` | 文書・テキストの終了。既定の生成終了IDにも含まれる |
| `<think>`、`</think>` | 推論文の範囲 |
| `<tool_call>`、`</tool_call>` | ツール呼び出しの範囲 |
| `<tool_response>`、`</tool_response>` | ツールの応答の範囲 |
| `fim_prefix/middle/suffix`等 | コードの穴埋め。前半・後半を与えて欠けた部分を補う形式 |
| `repo_name/file_sep` | コードのリポジトリ名・ファイル境界 |
| `vision/image/video`、`object_ref/box/quad`等 | 画像・動画・位置参照等の系列。語彙への登録は、このテキストモデルの画像処理能力を意味しない |

「1つのIDに登録された制御用の記号」と、tokenizer設定の`special=True`は区別する。
このリビジョンではthink・tool・FIM系の記号の多くは`special=False`である。
登録済みIDは機械的には選べるが、別用途に転用してモデルが正確に従うかは未確認。
今回調べた一覧に、汎用の「1引数の終了」専用トークンはない。
新しい名前を定数にしても、学習済みの1トークンが追加されるわけではない。

[生成終了の設定](https://huggingface.co/Qwen/Qwen3-0.6B/blob/c1899de289a04d12100db370d81485cdf75e47ca/generation_config.json)、
[Qwenの制御記号の説明](https://qwen.readthedocs.io/en/stable/getting_started/concepts.html#control-tokens-chat-template)、
[公式のFIM使用例](https://github.com/QwenLM/Qwen3-Coder/blob/main/examples/Qwen2.5-Coder-fim.py)。
制御記号の一般説明はQwen2.5を含む資料なので、登録・設定の事実は使用中のQwen3-0.6Bのファイルで確認した。

## 提案するデータの流れ

1. 名前選択は現在の方式を維持する。
2. 選択した関数の引数名・型・順序と依頼文を、引数生成用の1つの入力にする。
   出力はその順の値だけを、引用符外のLFで区切るよう指示する。
3. 引数ごとに文法を切り替えて`generate_value`を実行する。入力ID列は同じ応答の続きとして保持し、
   完成した中間表現とLFを次の引数の文脈に含める。引数ごとのメッセージ・プロンプトは作り直さない。
4. LFまでの値を型別に正規化する。生の中間表現は、次の生成に使うID列と診断用に保持する。
5. 最終JSONの`prompt`・`name`・キー・カンマ・括弧はコードが組み立てる。
   `Forced`は最終JSONの固定部分を表し、モデルの値列には追加しない。
   `ValueSlot`は名前と型を持ち、終端は全スロット共通のLFにする。
   正規化した値は`json.dumps`でJSON化して差し込む。
6. 全文を従来どおりJSONと動的Pydanticモデルで検証する。入力からのpromptコピー、原子的保存、
   件ごとのエラー処理は維持する。引数0個では値生成を行わず、定義から空のparametersを組み立てる。

最終JSONの骨組みと、モデルが読む中間表現を分ける変更である。
現在の`Forced`はID列にも追加されるが、この案では最終JSONだけに追加する。
生の生成表現をそのまま最終JSONへ連結する処理は置き換える。

## 型別の文法と終端

「1行」は1引数の記録を意味する。引用符内に実改行がある文字列では、1記録が複数の物理行にまたがる。
単純な`splitlines()`は使わず、引用符・バックスラッシュ・Unicodeエスケープ・UTF-8の状態を持つ。
引数の文法が完了できる状態で、引用符外のLFを生成したときだけ次の引数へ進む。

| 型 | 中間表現として許す範囲 | 正規化 |
| --- | --- | --- |
| number | 従来の符号・整数・小数に、英語形式の3桁区切りを追加。例: `2,000,000`、`-12,000.75` | 桁区切りの形式を検査してからカンマを除き、ADR-0017の値保持検査を通す |
| string | 二重引用符で囲む。従来のエスケープ・UTF-8に加え、引用符内の実LFも許す | 実LFをJSONのエスケープへ変換して文字列として読み取り、最終JSONでは`json.dumps`に任せる |
| boolean | 従来どおり`true`か`false` | boolとして保持 |

数値の拡張は桁区切りだけを対象とする。先頭プラス、指数表記、小数点としてのカンマは今回追加しない。
提案する桁区切りは先頭1–3桁が1–999、以後は3桁ずつ。小数点以下にはカンマを許さない。
`2,00`や`2,,000`をそのまま完了させたり、無条件にカンマを削除して受理したりしない。
文字列の`"2,000,000"`は書き換えない。`\"`では引用状態を閉じず、`\\n`のような文字列内の表現も区別する。
文字列の実LFは保持するが、エスケープ直後の不正な実LFや、その他の未対応の制御文字を一括で許す案ではない。

たとえば、中間表現の次の4物理行は、number・string・booleanの3引数を表す。

```text
2,000,000
"Tokyo,
Japan"
true
```

最終JSONのparametersは次になる。

```json
{"amount": 2000000.0, "place": "Tokyo,\nJapan", "enabled": true}
```

トークンの全バイトを検査し、1引数の外側の終端LFを越えて次の値まで書くトークンは拒否する。
完了判定は従来どおり次の候補取得より先。暫定256トークンは中間表現と終端LFを合わせて数え、
引用符内の改行で上限をリセットしない。桁区切りを許しても、モデルが誤った数値で終了する可能性は残る。
整数はintで保持し、小数はJSON再出力で値が変わらないことを確認する。
精度損失・非有限値・範囲外・未完了は理由付きのPromptErrorにする（ADR-0017）。

## 検証と未確認の点

実装時は先に、数値の接頭辞・桁区切りの完了、引用符内外のLF、エスケープされた引用符、
UTF-8分割、終端と次の値を含む結合トークン、上限直前・ちょうど・超過を直接テストする。
固定logitsの複数引数生成で、文法の切替、同じID列の継続、正規化、最終JSONの構造を確認する。
文字列・boolean・引数0個・任意のキー名・TUI・保存の回帰検査も行う。

精度は`2,000,000`、`-12,000.75`、区切りなしの対、カンマ・実LF・`\\n`を含む文字列などを使い、
既存方式と同じ依頼で比較する。数値は独立したDecimal比較で検査し、丸めを正答に数えない。

時間は精度測定を止めた単独実行で比較する。SDKはKVキャッシュを再利用せず、毎回全ID列をforwardする。
単に「1応答だから同じ時間」とは扱わない。forward回数・各入力長・forward累計時間・全体時間を別々に記録し、
現方式ではForcedも後続の入力長に影響する。この提案ではForcedをモデル入力から外すため、
追加する指示・LF・桁区切りのトークンと、取り除くJSON構造のトークンを含めて入力長を比較する。
計測用の観測が結果を変えないことも固定logitsで確認する。

特殊トークンの登録と既存SDKの停止・decode動作はファイルで確認した。
この改行方式の実モデル精度と時間、桁区切り付き数値の誤答頻度はまだ測っていない。
本提案は精度90%を基盤PRの承認条件に追加するものではない。
