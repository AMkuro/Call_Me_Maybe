# ADR-0004: 数値と型

状態: 決定(ユーザー、2026-11-08)。見直しの条件つき。

2026-11-10の設計更新: ユーザーの指定により、[ADR-0015](0015-value-records.md)では
`2,000,000`などの桁区切り数値を中間表現として許す。桁区切りの形式を検査してから
カンマを除き、有限のfloatへ正規化する。stringのカンマは保持する。
この範囲で下記の「生成中は厳密なJSON数値に限る」を置き換える設計で、コードは未変更。
対応する型とfloatの精度・範囲の扱いは維持する。

## 背景
- 【明文】引数の型は関数定義どおり(number、string、boolean など)(V.4.2)。Subject v1.7 の原文(PDF)で
  確認した。例では `2.0` と書かれている。
- 【解釈】整数相当の値を `2` と出すか `2.0` と出すかは未定義(`docs/subject-v1.7.md` 第9章の10)。
- 【測定】PoC のテストには boolean の引数があった。

## 決定
- 【設計判断】対応する型は **`number`、`string`、`boolean`**(ユーザー、2026-11-08)。
  他の型は、時間があれば追加で実装する。
- 【設計判断】それ以外の型(`integer`、配列、入れ子など)は、今は対応せず、起動時のエラーにする。
  - 【解釈】実在しうる型名は、JSON Schema の語彙なら `integer`、`array`、`object`、`null`。
    バイナリや16進数は型名ではなく、`string` の中身(または `format`)として現れる。
    レビューで使う型は不明。
  - 懸念: レビューの関数定義に `integer` などが含まれると、起動時エラーで全件が出力されない。
    `integer` は数字だけの文法で足りるので、追加は小さい変更。
- 【設計判断】デコードは JSON として厳密にする。
  - 数値は JSON の数値文法(`2` も `2.0` も可)。
  - boolean は `true` または `false` の2語のどちらか。
  - `True` や `"2"` のような近い表現は、**今は許さない**。
- 【設計判断】生成後、関数定義から作る pydantic のモデル(既定の変換)で検証する。宣言が `number` の
  引数だけを float にする。`string` と `boolean` の引数には触れない。出力は `json.dumps` により
  `2.0` や `true` となる。強制トークンの `.0` は使わない。
- 緩さ(pydantic のような変換)は、デコードでなく生成後の検証に持たせる。

## 見直しの条件(判断の基準)
### 近い表現を許すか
次のすべてが当てはまったとき、近い表現を許すことを検討する。

1. 全体の精度が目標(90%)を下回っている。
2. 失敗の解析で、原因の一部が「近い表現を許していないこと」だと分かる(例: 大文字の `True`、引用符つきの数)。
3. 許すことで他のケースが壊れない(テストで確認できる)。

閾値(失敗のうちの割合など)は、データを見て人間が決める。

### 型を増やすか
時間があれば、`number`、`string`、`boolean` 以外の型を追加で実装する。追加の順序は、評価で実際に使われる
関数定義に含まれると分かった型を先にする。

## 帰結
- 浮動小数点の表記は、Python の `json.dumps` に任せる。長い小数や指数表記は出さない文法にする。
