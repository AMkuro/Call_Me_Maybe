# ADR-0018: 隔離したローカルLLMのプロンプト改善

状態: **ユーザー承認済み**（2026-11-11）。

## 背景

基盤実装は未承認で、精度の改善は別の作業である。ユーザーは別worktreeで、
軽量なローカルLLMにプロンプトの編集・実行だけをさせることを要求した。
GPUの精度探索で改善すれば、CPUの指定環境と追加fixtureで確認したい。
本体更新は実験ブランチにも取り込み、pushやPRは行わない。

## 比較した選択肢

| 選択肢 | 利点 | 問題 |
| --- | --- | --- |
| 任意のファイル・コマンドを許す | 既存エージェントを使いやすい | 指定の権限を超え、採点や生成方式も変えられる |
| 各候補がsrc/prompt.pyを書き換える | 既存CLIで試せる | 並列で衝突し、変更範囲の保証が難しい |
| 固定制御の下でJSONの指示文だけを差し替える | 権限と比較条件を固定できる | 開発用の制御・実行経路を追加する必要がある |

## 提案

3番目を推奨する。`write_prompt` は2つの指示文字列だけを保存し、`run` は固定のGPU評価を呼ぶ。
採点・CPUへの昇格・追加評価・Git同期は信頼する制御側が担当し、LLMには操作させない。
本体のPython、SDK、生成方式、goldは変更しない。

当初は既存0.6Bを改善用にも使う案だったが、ユーザーが改稿能力の不足を懸念して撤回を指示した。
調査エージェントの比較に基づき、まずQwen3.5-9BのBF16・GPUを使う。
評価対象のQwen3-0.6Bは変更しない。モデル名や提供元のベンチマークだけで改稿能力を保証しない。
根拠・代替案・互換性の未検証箇所は[モデル調査](../../research/local-prompt-editor-models.md)に記録する。
候補の主評価は提供goldへの完全一致とし、正規表現の有限例での動作一致は別指標にする。
提供データに対する可換引数の別解を、結果を見て主得点に追加しない。

CPU時間はユーザー決定のphys16-t6実測＋8秒を使う（ADR-0010）。生の時間と別に保存し、
候補やGPUの並列性による競合を止めた単独実行にする。補正は既知の11件を根拠にした便宜的なもの。
追加の88件は同難度・未知入力の保証とはせず、探索終了後に開発例だけで選んだ1候補の確認に一度使う。
正規表現の表記だけの改善を、意味的な改善と呼ばない。
コード更新を取り込んだら基準と候補を測り直し、異なるコードでの比較をしない。

## トレードオフ・再検討

指示文だけに限定するため、一覧の書式・骨組み・デコード方式を変える改善は今回できない。
それらが必要だと実験で判明した場合は、実験の権限を黙って広げず、別の設計にする。
pilot-1の結果を受けた別の設計は[ADR-0020（提案）](0020-few-shot-and-relay.md)に置く。
追加fixtureを調整へ戻すなら評価集合としての用途を変更し、別の未使用集合を用意する。
モデルの改稿能力、並列GPUの実効性、改善の有無、CPUでの再現はまだ未検証である。

詳細は[設計案](../../superpowers/specs/2026-11-11-local-prompt-improvement-design.md)と
[fixtureの事前レビュー](../../research/calibrated-fixture-review.md)を参照する。

## 作業終了時点

再開指示後、レビュー指摘を再現するテストと修正を加え、174テスト・lintを通過した。
Qwen3.5-9BのGPUロードと短いJSON生成まで確認した。精度探索は別の実測として残す。状態と再開手順は[引継ぎ](../../handoffs/2026-11-11-local-prompt-improvement.md)を参照する。

改善側の実行方式は、後続のユーザー指定により[ADR-0019](0019-optimizer-kv-cache.md)へ更新した。
独自のエージェントループを削除し、既存OSSの設定と2ツールを使う。
