# ADR-0016: 関数名から定義を取り出す辞書

状態: ユーザー決定（2026-11-10）。「辞書を使うようにしよう」と実装を指示した。

## 背景と選択肢

入力JSONは関数の配列で、既存コードは検証後も`list[FunctionDef]`を保持する。
モデルが名前を選んだ後、同名の定義を毎回先頭から探すため、関数数Fに対して最悪O(F)となる。

- 配列のまま検索する: 保持方法は単純だが、既知の名前を使って再走査する。
- 名前から添字を引く辞書を併用する: 検索は平均O(1)だが、配列との対応を保持する必要がある。
- 名前から定義を直接引く辞書を使う: 検索は平均O(1)で、添字や二つの保持先は不要。

ユーザーが、最後の方式を採用した。入力JSONと最終出力の形式は変更しない。

## 処理と受け渡し

1. `load_functions`は従来どおりJSON配列をPydanticで検証する。
2. `index_functions`が空・空白だけの名前と重複を拒否し、`dict[str, FunctionDef]`を作る。
   同名の値を上書きして受理しない。測定ツールのfixtureにも同じ対応付け処理を使う。
3. `main`は辞書のキーから名前の木を作る。`build_name_prompt`は`values()`で定義を列挙し、入力順を保つ。
4. `select_name`は名前の木とモデルで選択し、選んだ名前をキーに定義を取り出す。
   `process_prompt`にも同じ辞書を渡す。選択方法・生成文法・出力先の処理は変更しない。

辞書の要素は検証したFunctionDefへの参照で、同じ定義を別に複製しない。
辞書の管理領域は必要だが、常用する配列と辞書の二重管理は行わない。

## 検証と限界

読み込み後の順序と直接参照、重複・空名の拒否、プロンプトの掲載順、固定logitsでの選択と
定義の受け渡し、測定fixtureの重複拒否を検査する。既存の観測・制約・保存の検査も維持する。

読み込みと全関数を載せるプロンプト作成は引き続きO(F)。改善対象は選択後の定義検索で、
forward回数は減らない。全体の速度改善は未測定であり、この変更だけで速度目標を達成するとは判断しない。
同名の扱いや入力順を変える必要が生じた場合は、この契約を見直す。
