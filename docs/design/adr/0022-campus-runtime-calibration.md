# ADR-0022: 校舎CPUでの所要時間を検証する方法

状態: 提案。所有者の設計承認待ち（2026-11-11）。

## 背景

Subjectは標準的なハードウェアで全テストプロンプトを5分未満とする。
取得した校舎・開発機のNumPy測定では、メモリ・行列計算の時間比が負荷ごとに異なる。
開始終了温度はあるが、実アプリの温度曲線と性能低下率は測れていない。
検証した資料、計算値、追加調査の契約は[診断と設計案](../../research/campus-runtime-feasibility.md)を参照する。

## 選択肢とトレードオフ

1. **KVM等のVMへ校舎のOS・容量・vCPU設定を移す。** OSと依存は隔離できる。
   AMDの実行特性・メモリ・冷却をIntel実機と同じにはできず、実機による校正が残る。
2. **実機で測り、既存のCPU環境をcgroupとスレッド数で校正する（推奨）。**
   現在の道具を使え、5分判定に必要な実アプリの差を直接検証できる。
   検証した負荷と熱状態の範囲を明示する必要があり、未知入力の保証にはならない。
3. **校舎の直接測定だけを採用する。** 転用誤差を避けられるが、開発中の比較に校舎アクセスが必要になる。
   選択肢2の近似が検証で合わなければ、この方法に戻す。

詳細なCPU・熱シミュレーターを新設する方法は、校正情報と実装・検証の費用が大きいため、今回の推奨に含めない。

## 決定案

所有者へ選択肢2を提案する。実アプリを子プロセスとして実行し、温度・CPU・メモリ・制限の時系列と
正常終了までの壁時間を記録する`observe`モードを既存の調査器へ追加する。
既存の短いNumPy測定の形式・原記録は保持し、`src/`・SDK・依存関係は変更しない。
校舎で通常開始時と温まった時の測定を行い、開発機の近似を調整に使わない入力でも検証する。
許容誤差と時間の余裕は所有者が承認する。取得不能な温度・電力・周波数情報は欠測として残す。

この案は未決定である。「phys16-t6の総時間＋8秒」という所有者の既存の暫定方針を変更しない。
校舎用の常時表示器を別途作る以前の方針との関係も、承認時に確認する。

## 見直す条件

- 調整に使わない入力や温まった条件で差が許容範囲を外れたら、単一設定による近似を採用しない。
- 校舎アクセスが使えない場合は未検証と報告し、開発機の測定を実機の証拠へ置き換えない。
- OS差の影響を切り分ける必要が出たら、VMを追加する。温度再現の根拠には使わない。
- 入力長・forward回数による違いを総時間だけで説明できなければ、公開APIを使う追加計測を設計する。
