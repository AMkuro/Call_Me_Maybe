# ADR-0011: 関数名の木の作り方、出力先、モデルのラッパーの形

状態: 決定(ユーザー、2026-11-09)。ADR-0001(案 a)、0007、0009 を具体化する。

## 背景
- ADR-0001 の案 a は、関数名を `encode` でトークン列にして木を作る。名前のすぐ後には、閉じ引用符とカンマ
  (`",`)が来る。
- 【測定】(2026-11-09、サンプルの関数名 5 つ)`",` は 1 トークン。名前だけを `encode` した列は、名前 + `"`、
  名前 + `",`、名前 + `", "parameters": {` のどれの列の接頭辞にもなっていた。語彙 151643 のうち、引用符と
  他の文字を含むトークンは 1343 個。
- Subject IV.3.1 の原文は "All classes must use pydantic for validation."。モデルであることまでは求めていない。
- Subject は出力パスの記述が曖昧(`docs/subject-v1.7.md` 第9章)。

## 決定
1. **木は名前のトークン列だけで作り、葉に着いたら選択を打ち切る。** `",` 以降は骨組みとして強制する。
   名前同士の接頭辞の衝突は起動時エラー(loader)。
2. 起動時に、各名前について「名前だけの列が、名前 + `",` の列の接頭辞か」を確かめる。違う名前があれば
   エラーにする(接頭辞にならない名前を黙って通さない)。
3. 出力先の既定は `data/output/function_calls.json`。曖昧な Subject の、最も明確な解釈を採る。
4. モデルのポートは `typing.Protocol`。ポートの入出力と設定は pydantic で検証する。例外クラスも、持たせる
   データを pydantic で検証する形で足りるとみなす。(Protocol は、下の更新案で取りやめた。)
5. `src` から `import torch` しない。

## 理由・トレードオフ
- 打ち切りは、選択と骨組みの境目を 1 つにし、強制するトークンの数を減らす。
- トークン単位の木は、各節で子のトークン ID だけを許可する。語彙を全部調べずに済み、正規の分割だけを許す。
- 代償: 別の分割は許さない。名前が `"` と結合する語彙の例外は、2 の確認で起動時に落とす。
- 4 の解釈と防御: Subject の文言("use pydantic for validation")は定義が曖昧。「データを持つクラスは pydantic で
  検証する」と解釈し、検証するデータを持たないラッパー `Model` と、メッセージだけの例外は対象外とする。防御は原文の語句による。
  他の決定(ADR-0002、0004 の pydantic による事後検証。`cli`、`schema`、`name_trie` などの pydantic 化)と
  矛盾しない。レビュアーの読み方は確かめられない。

## 見直しの条件
- 2 の確認で落ちる名前が現れたとき(`",` まで含めて木を作る案に戻す)。
- レビューで、`Model` や例外が pydantic の規則に触れると指摘されたとき(pydantic のモデルに替える。未検証)。
- 実測はサンプル 5 名のみ。レビューの関数セットで確かめていない。

## 更新案(2026-11-09)
上の決定 1・2 は、下の案 B で置き換える。決定 4 の Protocol は、下の「モデルのポート」で取りやめる
(経緯が分かるよう、本文は残す)。案 B、P1、ポートの取りやめは決定。

### 案 B(決定。ユーザー、2026-11-09。「案 B でもいい」)
- 木を `encode(名前 + 終端)` で作り、終端の後ろを葉にする。`fn_add` と `fn_add_numbers` のように、名前が別の名前の
  接頭辞でも、「ここで終わる」と「続ける」をモデルが選べる(ADR-0001 の元の方針)。
- 決定 1 の「接頭辞の衝突は起動時エラー」と、決定 2 の確認は要らなくなる。空・重複・未対応の型のエラーは残す。
- 現状(名前だけの木)の問題: 名前が別の名前の接頭辞だと、葉で打ち切るので、長いほうの名前に届かない。
  決定 1 のエラーは、これを黙って通さないためだった。ただし、レビューで関数セットが変わる(Subject V.2)ので、
  合法な関数セットが起動時に落ちる恐れがある。
- 【解釈】(ユーザー)Subject が求めるのは「無効トークンの logits を負の無限大にして、残りから選ぶ」(V.1、V.3.3)で、
  JSON 全体を LLM が出すことではない。名前の終わりを示す記号が決まっていれば、その形は `",` でなくてもよい。
- 未解決: 終端の選び方。`",` は、全文の中での分割が、単独のエンコードとずれる恐れがある(5 名でしか測っていない)。
  別の記号を使うなら、後ろの骨組みとのつなぎ方(トークン列をつなぐか、全文を再エンコードするか)を決める。

### モデルのポート(決定: ポートの型をやめる)
- 【設計判断】(ユーザー、2026-11-09)決定 4 の Protocol をやめる。モデルは、`llm_sdk` を包む具体的なラッパー
  `Model`(`model_port.py`)にする。理由: テストのために設計を曲げている。Protocol が防ぐのは、mypy がテストの偽物を
  弾くことだけで、モデルを差し替える要件は Subject にない(Qwen3 と `llm_sdk` が決まっている)。
- テストの代わり: 純粋な部分(木、マスク、骨組み、検証)は、logits をデータとして渡して直接確かめる。ループ
  `decoder.generate` は `logits` の関数だけを受け取るので、固定値を返す関数で確かめる。全体は、実モデルの出力を
  `json.loads` とスキーマで確かめる。
- pydantic の規則: `Model` は SDK のハンドルを持つが、検証するデータを持たないので、対象外と解釈する(上の「4 の解釈と防御」)。
  【設計判断】(ユーザー、2026-11-09)検証しないクラスに pydantic を足さない。理由: 規則は「検証に pydantic を使う」で、
  検証しないなら依存を増やす必要がない。`PrivateAttr` を使う案と、`Input.Model` の入れ子案は採らない。検証する設定(モデル名や
  保存場所など)が必要になったら、設定だけを pydantic のクラスにして `Model` に渡す。
- 見直しの条件: 純粋な部分のテストだけでは、制約の性質を確かめきれないと分かったとき。

### 該当なし・低信頼のときの扱い(決定: P1)
- 【設計判断】(ユーザー、2026-11-09)許可された候補が、どれも低い(モデルが木の外のトークンを望んでいる)ときも、
  貪欲に最大の候補を選んで出力する。標準エラーに警告を出す(P1)。
- 理由: Subject は、該当する関数がないプロンプトの扱い(スキップするか)と、90% の分母を定義していない
  (`docs/subject-v1.7.md` の未定義の項目 5、6)。スキップが誤答より良いか分からないので、情報を捨てない側を採る。
- 見直しの条件: 該当なしのプロンプトを含む入力で測り、誤った記録の害が大きいと分かったとき(スキップする P2 に替える)。
- 検出の案(未決): 許可トークンの確率の占有率(語彙全体の softmax のうち、許可トークンの分の和)を標準エラーに出す。
  閾値は、実モデルで測ってから決める。プロンプトの形でも低く出うるので、「該当なし」とは限らない。
- 採らない案: 許可された候補のうち、logits が極端に低いものを除く。貪欲選択は最大のものを選ぶので、効果がない
  (【解釈】)。
