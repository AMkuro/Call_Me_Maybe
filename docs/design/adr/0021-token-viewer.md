# ADR-0021: トークン選択を段階表示する別プロセスのビューア

状態: **提案**(2026-11-12)。ユーザー決定済み: 有効化の手段を設けず自動で適用し、ビューアが
なければ今の表示に戻す / Rich は `dependencies` に入れる / 表示時間は CLI ではなく、名前の付いた
プログラム内の定数にし、後で調整する / 受け渡しは Unix ソケット(すべて 2026-11-12)。
D5 の読み方もユーザーが確認した(2026-11-12)。実装の開始はユーザーの指示を待つ。

## 背景と要求

ADR-0014 の stderr 表示は 0.05 秒ごとに再描画するため、トークンの選択過程を目で追えない。
ユーザーは、各トークンで「制約前の候補 → マスク → マスク後の順位 → 採用」を、
生成中の JSON と並べて観察できるデバッグ用 TUI を求めた(2026-11-12 の依頼)。
ADR-0014 の表示は、ビューアがないときの表示としてそのまま残す。

- 【明文】ボーナスに "Visualization of the generation process" がある(VII)。
- 【明文】"You are allowed to use other functions and libraries to complete the bonus part,
  as long as their use is justified during your evaluation."(VII)。
  ローカル要約 `docs/subject-v1.7.md` はこの一文を落としていたため、同時に追記した。
- 【明文】必須部分の CLI・出力・5 分以内は変えてはならない(IV.3.2、V.4、V.5)。

依頼の要件(要約): 生成と表示を別プロセスにし、生成側に `sleep` を入れない。ビューアが
遅れても生成を待たせず、イベントを失わない。ビューアがなくても通常実行が動く。
候補は最大 10 行で Token ID・トークン・logit。強制トークンは `FORCED` と出し、logit を捏造しない。
観測のための追加 forward をしない。表示によって選択を変えない。
デバッグ機能を使わないときは、不要な logits の診断をしない。

## 設計

### データの流れ

```text
ビューア (python -m src.viewer、先に起動)          生成プロセス (python -m src、引数は従来どおり)
 Unix ソケットで待ち受ける                           プロンプトの開始ごとにソケットへ接続を試す
 受信スレッド: 届いた行をすぐメモリの列へ積む          ├ 接続できた: 候補を取り出し、1 トークン = JSON 1 行を送る。
 表示: 列から 1 件ずつ取り、                         │            stderr は警告・結果・エラーの通常ログだけ
   RAW → MASK → SORT → SELECT を時間をおいて描く     └ 接続できない・途中で切れた: 今の stderr 表示(ADR-0014)。
                                                                 候補の計算もしない
```

### 生成側の変更(最小)

1. `decoder.generate` に `top_k: int = 0` を足す。`top_k > 0` かつ許可候補が 2 つ以上のときだけ、
   すでに手元にある logits から次を計算して `TokenChoice` に入れる。モデルは呼ばない。
   - `raw`: 全語彙の logit 上位 `top_k` の `(id, logit)`。`np.argpartition` で O(語彙)。
   - `raw_allowed`: `raw` の各 id が許可集合に入るか。
   - `masked`: 許可集合の中の logit 上位 `top_k` の `(id, logit)`。許可集合全体から取るので、
     raw 上位 10 に入らなかった候補も出る(依頼の Phase 3 の条件)。
   選択は従来どおり `choose_token`(マスク後 argmax)で、上の計算は選択に使わない。
   強制(許可 1 つ)では従来どおり `next_logits` を呼ばず、候補は空のまま。
2. `top_k` はビューアに接続できている間だけ 0 より大きくする。ビューアがなければ、追加の計算はない。
3. `pipeline` の観測関数が、`vocab` のバイト列からトークン文字列を作り、JSON プレビュー
   (下記)を付けて `report("trace", <JSON 1 行>)` を呼ぶ。`report(label, text)` の形は変えない。
4. `display.terminal_progress` がビューアとの接続を持つ。接続中は `trace` を送り、stderr には
   今のリダイレクト時と同じ通常ログ(関数名・警告・結果・エラー)だけを出す。送信の `OSError`
   (ビューアの終了など)では接続を捨てて、今の表示に戻る。結果の保存には影響しない。
5. CLI は変えない。

### イベント(1 行 1 JSON)

```text
{"event": "prompt", "index": 2, "total": 5, "prompt": "東京の気温を調べて"}
{"event": "token", "stage": "generate_parameters", "parameter": "city (string)",
 "step": 7, "forced": false, "selected": [12345, "京"],
 "raw": [[12345, "京", 10.92, true], [999, "\n", 10.1, false], ...],
 "masked": [[12345, "京", 10.92], [542, "都", 9.81], ...],
 "fixed": "{\"prompt\": \"…\", \"name\": \"get_weather\", \"parameters\": {\"city\": \"",
 "value": "東京", "rest": "}}", "done": false}
{"event": "result", "text": "get_weather {\"city\": \"東京\"}"}  /  {"event": "error", ...}
{"event": "end"}
```

- `fixed` は確定済みの部分(入力のコピー、スケルトン、生成済みの前の値)。`value` は今の値として
  モデルが生成したバイト列。`rest` はスケルトンの残り(未生成の値は `…`)。左ペインは
  `fixed` を通常色、`value` を強調色、その直後にカーソル `▌`、`rest` を薄い色で描く。
  どれも生成側が実際のトークン列とスケルトンから作るので、表示が生成と食い違わない。
- `value` は `bytes.decode("utf-8", "backslashreplace")`。UTF-8 の途中のバイトは `\xe6` の形で見え、
  文字がそろった時点で文字になる。JSON エスケープ(`\"` など)はモデルが出したとおりに見える。
- `select_name` では `value` が名前の接頭辞、`done: true` が終端トークンで名前が確定した印。
- `-∞` は送らない。MASK 段階はビューアが `raw_allowed` から作る。
- 語彙ファイルにない id(特殊トークン)は `<id 151645>` の形にする。
- 1 イベントはおよそ 1 KB。既知の 11 入力で数百トークンなので、ビューアのメモリに積む量は
  1 MB 未満の見込み(【推論】。実装後に測る)。

### ビューア(`src/viewer.py`)

- Rich の `Live`・`Table`・`Layout` だけを使う。キー操作はない。
- 起動するとソケットで待ち受け、生成プロセスの接続を受ける。受信スレッドは届いた行をすぐ
  メモリの列へ積むので、表示が遅れても生成側の送信は待たない(カーネルのバッファが詰まらない)。
  表示は列から順に 1 件ずつ取る。順序は 1 本の接続の順のまま。
- `token` イベントごとに 4 段階を描く:
  - RAW: `raw` を元の順で。
  - MASK: 同じ順のまま、不許可行を `-∞`・取り消し線・薄い色にする。
  - SORT: `masked` を表示(許可集合全体の上位 10)。これは表示上の段階で、デコーダーは argmax で
    選んでおり並べ替えをしていない、と画面下に一言出す。
  - SELECT: `masked` のうち `selected` の行を強調し、左ペインに選択を反映する。
  - FORCED: 候補表に「FORCED(logits は計算していない)」とだけ出し、SELECT の時間だけ表示する。
- 表示時間は、名前の付いた定数として `src/viewer.py` の 1 か所に置く。初期値は依頼の
  RAW 0.4 / MASK 0.4 / SORT 0.3 / SELECT 0.4 秒で、後でユーザーが調整する。
- トークン文字列は既存の `display._visible` で制御文字をエスケープし、引用符で囲んで空白・改行を
  見えるようにする。表の幅は Rich に任せ、`_clip` と `render_progress` は使わない(Rich が CJK 幅を数える)。
- 生成プロセスが終わっても、列に残ったイベントは最後まで表示する。`end` の後は最後の画面のまま
  次の接続を待ち、Ctrl-C で終わる。

### 変えないもの

CLI、`TokenChoice` の既存項目と `allowed_mass` などの診断、ビューアがないときの stderr 表示、
入出力 JSON、保存処理、SDK(非公開 API は使わない)。

## 決めること

### D1. プロセス間の受け渡し(決定: Unix ソケット)

ユーザー決定(2026-11-12)。最初の意向は「ソケットがよいが、面倒ならファイル」。自動で適用し、
ビューアがなければ今の表示に戻す、という決定が加わったため、下の比較でソケットを選んだ。

| 案 | ビューアの有無の判定 | 遅いビューア・後から起動 | 追加の量 |
|---|---|---|---|
| **Unix ソケット(推奨)** | 接続できるかで分かる。切れたら送信が `OSError` になる | ビューアの受信スレッドが積むので生成は待たない。後から起動した場合は次のプロンプトから見える | 生成側: 接続と送信、数行。ビューア側: 待ち受けと受信スレッド |
| JSONL ファイルの追記 | 分からない。ビューアがいなくても毎回書き、候補も毎回計算することになる(「使わないなら診断しない」に反する)。判定のために目印のファイルを足すと、ビューアが落ちたときに古い目印が残る | ファイルがバッファになり、最初から見られる | 生成側: 追記だけ。ビューア側: 末尾を追う読み込み |

ソケットの注意点(【解釈】): ソケットのファイルは、ビューアが起動時に古いものを消してから作る。
置き場所はユーザーごとの一時ディレクトリ(`tempfile.gettempdir()`)で、macOS のパス長の上限
(104 バイト)に収まる。Windows は対象外(AF_UNIX を前提にする)。

### D2. 有効にする方法(決定: 設けない)

ユーザー決定(2026-11-12): 有効化の手段は設けない。ビューアがあれば自動で使い、なければ今の表示に戻す。

### D3. 候補の計算の切り替え(D2 の決定で解消)

上位 10 件の取り出しはモデルの推論ではなく、手元の logits に対する NumPy の計算
(1 トークンあたり約 1 ms と見積もった。【推論】未測定)。ビューアに接続している間だけ行う。

この計算が要る理由: デコーダーは選択のために argmax(最大の 1 件)しか求めないので、
上位 10 件とその logit はどこにも残らない。logits は生成プロセスの中にしかなく、
全語彙(約 15 万個の数値)を毎トークン送るのは依頼が禁じている。上位 10 件を表示するには、
生成側で全語彙から上位 10 件を選び出す計算(`np.argpartition`)が必ず要る。
【測定】今の `generate` も、`report` があれば(通常実行では常に)毎トークン全語彙の `np.exp`
(`allowed_mass`)を計算しており、追加はそれと同程度の量になる見込み(【推論】)。

### D4. Rich の依存の置き方(決定: `dependencies`)

ユーザー決定(2026-11-12)。【測定】`uv.lock` で `rich` は SDK の依存の連鎖(`typer` 経由)で
すでに入っており、`.venv` に `rich-15.0.0` がある。新しいインストールが増えないことは、
実装時に `uv lock` の差分で確かめる。import するのは `src/viewer.py` だけ。

### D5. 表示時間の調整(決定: 名前の付いた定数)

ユーザー決定(2026-11-12): CLI などの外からの指定にせず、プログラム内の定数にする。
マジックナンバー(処理の途中に直接書いた数値)にしない。時間は後でユーザーが調整する。
名前の付いた定数を `src/viewer.py` の先頭の 1 か所にまとめ、処理の中には数値を書かない
(エージェントの読みを、ユーザーが 2026-11-12 に確認した)。

参考(【推論】): 初期値では 1 トークン 1.5 秒なので、1 プロンプト 40 トークンなら約 1 分かかる。

### D6. 依頼から外す点(決定)

ユーザー承認(2026-11-12)。次は入れない。

- 過去イベントの履歴、ステップ送り、検索(依頼でも不要とされている)。
- 端末ウィンドウの自動起動(不要とされている)。
- `TokenChoice` へのトークン文字列の追加: 文字列は pipeline が `vocab` から付ける。decoder は数値だけを扱う。

## 検証計画

依頼の検証項目との対応。実モデルを使わない項目は固定 logits と模擬イベントで確かめる。

| 項目 | 方法 |
|---|---|
| 1 RAW 上位 10 / 2 MASK / 3 SORT | `generate` に固定 logits を渡し、`np.argsort` で全探索した期待値と比べる。raw 上位外の許可候補が `masked` に入るケースを含める |
| 4 SELECT の一致 | `selected` と `choose_token` の結果、生成されたトークン列を比べる |
| 5 強制で追加推論なし | 許可 1 つのとき `next_logits` が呼ばれないことを呼び出し回数で確かめる |
| 6 名前のプレビュー / 7 値のプレビュー | 最後の `token` イベントの `fixed + value + rest` が出力 JSON と一致する(実モデルの実行 1 回 + 模擬) |
| 8 待たせない | 受信だけして表示しないビューア役のソケットに大量のイベントを送り、送信が詰まらないことを確かめる。実モデルでビューアあり・なしの生成時間を比べる |
| 9 結果が変わらない / 10 ビューアなしで成功 | ビューアあり・なしで出力 JSON を `diff`。途中でビューアを止めても保存されること |
| 11 終了後も最後まで表示 | 生成プロセスの終了後も、列に残ったイベントを全部描くことを確かめる |
| 12 日本語・制御文字・長いトークン | 描画関数に `"\x1b[2J"`、`"\n"`、CJK、長い文字列のトークンを渡し、出力に生の制御文字がないことを確かめる |

計時は ADR-0010 に従い、精度の確認と分けて記録する。

## 見直す条件

- ビューアのメモリが想定より増える(長い値、多数の入力)とき: `raw` を 10 から減らすか、`fixed` を差分にする。
- 評価機で Rich の版が変わり表示が崩れるとき: 版を固定する。
- 評価機で AF_UNIX が使えないとき: D1 のファイル案に戻す。
