調べたこと: Qwen3-0.6B で関数呼び出し JSON を作るとき、A（1段）・B（番号で選ぶ）・C（名前で選ぶ）の差は何に由来し得るか。トークン境界・選択の偏り・小さなモデル・引数・時間の5点を、原文で確かめる。

文法の端とサブワードトークンのずれ（トークンの不整合）は、制約付き生成の精度を大きく下げることがある根拠あり

A と C で『結合トークンを許す』直しが大きく効いた現象と同じ種類の指摘。強制した固定文字列を、モデルの自然なトークン化と違う形で入れる問題は、SGLang の jump-forward の説明にも出てくる。

値の先頭の空白を含むトークンを許すと性能が上がる一部のみ

原文の1文だけを切り出した。どのタスク・どの割合で効くかは、この抜き書きだけでは分からない。

文法を課すデコードは、LLM が学んだ分布をゆがめて、性能を損なうことがある根拠あり

A・B・C はどれも『有効なトークンの中で argmax』なので、この指摘は3方式すべてに関わる。方式ごとの違いは、この論文では扱っていない。

選択肢の ID（A/B/C/D など）への偏りは、位置よりも ID トークンへの事前の偏りが主因だと報告されている根拠あり

B（番号で選ぶ）の位置偏りの説明を直す材料。ID を使わない選び方は、この偏りを避けられる、という報告も同じ論文にある。BiasBusters は、ツール選択でも位置の偏りがあると述べる（先行研究の紹介）。

関数名を複数トークンで作らせると誤りが出るので、関数ごとに専用のトークンを割り当てて1トークンの分類にする手法がある（学習が必要）一部のみ

関数名を選ぶ段（C）の弱点と、番号で選ぶ段（B）の考え方の中間にある手法。専用トークンの追加とモデルの変更を含むので、公開 SDK だけでは再現できない。

小さな言語モデルは、ゼロショットから few-shot で改善するが、出力の形式を守るのが苦手根拠あり

A・B・C はどれも形式を制約付きデコードで担保しているので、この弱点は文法側で消している。few-shot の効果の大きさは、この抜き書きでは分からない。

必要な関数だけに絞るとプロンプトを短くできる（ツール検索）一部のみ

TinyAgent は小さな分類モデルで関数を絞る方式。今回の課題では関数選択を LLM に任せる決まりなので、そのまま使えるとは限らない。短くすると精度も上がる、という書き方に留まる。

自然言語から正規表現を作るとき、最も多い誤りは * の位置の誤りや不要な追加だった（強いモデルでの観察）一部のみ

小さなモデルでの測定ではない。vowel を [aeiou] ではなく aeiou とする誤りなど、私たちの失敗とは種類が違う可能性がある。

出力の形式を厳しくすると、推論の性能が落ちることがある一部のみ

図1の説明から1文だけを切り出した。どれくらい落ちるかはこの抜き書きでは分からない。

プロンプトに入れる関数（ツール）が多いほど、関数呼び出しの精度は下がる。小さなモデルほど影響が大きいとも報告されている根拠あり

A・B・C は、関数一覧とスキーマを毎回プロンプトに入れる。今回の関数セットは小さいが、評価で関数が増えたときの影響を見る材料になる。B・C の2段目は選んだ1関数だけをプロンプトに入れる設計なので、この点で有利になり得るが、論文はこの設計を比べてはいない。

プロンプトが長いほど精度が落ちる。小さなモデルはプロンプトの長さに敏感だとされる一部のみ

aPSF の付録の実験は Llama-3.1-8B-Instruct の GSM8K（算数）で、0.6B の関数呼び出しではない。『500トークンを超えると大きく下がる』という本人たちの表の注記。私たちの A の v5（約550トークン）と同じ水準なので、参考にはなるが、同じ現象とは言えない。

1B未満の超小型モデルは、1〜3Bのモデルより関数呼び出しの精度がはっきり低い根拠あり

Qwen3-0.6B は『1B未満』に入る。この論文はファインチューニングを含む比較で、制約付きデコードのみで補う私たちの設定とは条件が違う。

オンデバイスの推論では、プロンプトの処理（prefill）が全体の遅延の大半を占め、その時間はプロンプトの長さに比例する根拠あり

KV キャッシュ無しの私たちの設計では、生成のたびに全系列をもう一度処理するので、この比例の影響をさらに受ける（これは論文の主張ではなく、私たちの設計についての推論）。CPU・KV キャッシュ無しで文法制約つきデコードの時間を測った研究は、探した範囲で見つかっていない。

Qwen3-0.6B を、制約付きデコード無しの道具利用ベンチマークで測った結果がある。道具1回の呼び出しの段（A）で 44%、道具を使わない段（A0）で 80%、2道具の連鎖（B）で 39%、分岐のある段（C）で 4%根拠あり

AgentFloor は Ollama 上の通常のツール呼び出しで測ったと読める（制約付きデコードの記述は未確認）。私たちの課題は『道具1回の呼び出し』（A の段）にあたり、制約付きデコードと関数セットが違うので、数字はそのまま比べられない。それでも、素の 0.6B は単純な呼び出しでも 44% 前後であり、文法で補う意味を示す材料にはなる。

ツールの候補を必要な数に絞ると、LLM が正しいツールを選ぶ割合が上がる（強いモデルでの測定）一部のみ

Claude Sonnet 4.6 での検証で、0.6B の結果ではない。今回の課題では関数選択を LLM に任せる決まりなので、事前に絞る方式は使えない可能性が高い。

選択肢を記号（A/B/C）で答えさせる方式は、記号と選択肢を結びつける能力（MCSB）が要り、その能力はモデルによって大きく違う根拠あり

B（番号で選ぶ）は、この MCSB に頼る方式にあたる。この論文で試したのは大きなモデル（GPT-3 系・Codex・InstructGPT）が中心で、0.6B の結果ではない。記号を使わず内容そのもので選ぶ方式（cloze、C に近い）は、この論文では『従来の方式』として比較されている。

0.5B・1B の小さなモデルでは、in-context の例を 10 個から 1 個に減らすと、関数型の課題の精度が目に見えて下がる一部のみ

モデルは一から学習した 0.13B/0.5B/1B で、課題は Todd らの関数ベクトル用の課題（ツール呼び出しではない）。制約付きデコードは使っていない。

選択肢のラベルを数字にすると、3-shot の例を足しても精度は偶然並みのまま改善が有意にならない（Qwen 0.5B〜72B を含む 20 モデル）一部のみ

題材は MMLU などの多肢選択で、制約付きデコードは使っていない。B の番号選択に近い形式だが、関数選択そのものではない。

KV キャッシュが無いと、生成の時間は全体のトークン数の2乗に比例する（有ると線形）一部のみ

理論の式による説明で、実測の時間ではない。制約付きデコードのマスク計算は含まない。実装によって係数は変わる。

0.6B〜4B のモデルでの制約付きデコードのオーバーヘッド: XGrammar は 1.6〜3.7%、Outlines は 9〜13% のスループット低下（測定環境は「consumer hardware」とだけあり、CPU かは未記載）一部のみ

KV キャッシュ有りの通常の実装での比率。キャッシュ無しの CPU での時間ではない。

Qwen3-0.6B を 4 コア CPU で関数呼び出しに使うと、1 クエリあたり平均約 46〜48 秒（ブログの測定）一部のみ

〔本人〕ブログ。制約付きデコードは使わない。KV キャッシュは通常有り。ブログ自身が、最初の実装で EOS が出ず 256 トークンを使い切り約 230 秒かかったバグを報告している。

関数定義を1トークンにして静的プロンプトを約95%減らしても、タスク完了の精度の低下は小さい（CAMPHOR）一部のみ

On-device のエージェント論文で、1つの課題設定。制約付きデコードではなく、小モデルの微調整が前提。

ツール名を trie で、引数を有限状態機械（FSM）で制約し、学習も長いプロンプトも使わずに構文エラーを無くす方式がある（ToolDec）。C の「関数名を選ばせてから引数」と同じ形にあたる根拠あり

対象は 7B 級が中心で、0.6B の結果ではない。CPU 時間の記述は無い。

制約のマスク計算は、1トークンあたり μs 単位（trie 0.65 µs、XGrammar 5〜10 µs、LLGuidance 73〜141 µs）で、モデルの前向き計算（GPU で約 10 ms）より桁が小さい一部のみ

GPU サービング（Qwen3-8B）での測定。KV キャッシュ無しの CPU ではない。ただしマスク計算の項は、前向き計算に比べて小さいという大きさの目安になる。

制約付きデコードの利得は、学習データや例が少ない条件で大きい（意味解析のベンチマーク BenchCLAMP）一部のみ

対象は意味解析で、モデルは GPT-3/Codex/BART 級。0.6B ではない。『例の数を変えた』比較ではなく、データ量の比較。

約1Bの小さなモデルで、0-shot→4-shot は +9.4 点、制約付きデコードは +3.8 点。4-shot は推論時間が平均 53% 増え、制約付きデコードは実行時間に有意な影響がない根拠あり

Gemma-3 1B、Qwen3、Llama-3.2 1B 等で、医療 NLP の抽出課題。vLLM と outlines を使った GPU サービング。関数呼び出しではない。『制約付き＋少数ショット』の併用が最も良い（+13.2）とも書いてある。

文法制約つきデコード（GCD）は、0-shot でも制約なしの 5-shot より精度が高いことが多く、利得は小さいモデルと少ない shot ほど大きい。shot を足す相対的な改善は、GCD のほうが小さい根拠あり

論理式への変換（FOLIO・GSM-symbolic）。2B〜14B 超のモデル。0.6B ではない。

制約付きデコードは、in-context の例を増やしたときの改善が、制約なしより急である（4〜8B のモデル、k=1〜9）一部のみ
