# ローカルLLMによる隔離したプロンプト改善

状態: **提案・設計承認待ち**。2026-11-11。
本体の基盤実装の承認とは別の、開発専用の実験ツールである。
この文書の作成時点では自動改善ツールを実装せず、モデルによる改善実験も行っていない。

## 要求との対応と作業場所

ユーザーの要求は、新しいworktreeで、小さなローカルLLMにプロンプト編集と実行の2ツールだけを
持たせ、GPUで候補を比較し、改善した候補をCPUの指定環境と追加fixtureで確認すること。
本体コードが未承認でも実験を独立して進められるようにする。
Subjectの意味的正答・JSON適合・5分未満は、それぞれ別の指標として測る。
実験ツールの依存・コードは提出アプリに追加せず、SDKと制約付き生成を変更しない。

- ブランチ: `exp/local-prompt-improvement`。
- worktree: 元のリポジトリの `.cache/worktrees/prompt-improvement`。
  既にignoreされ、lintからも除外される場所を選び、元の作業ツリーを変更しない。
- 起点: 実行に必要な現実装がある `origin/feat/implementation`。
  `origin/develop` はスケルトンまでなので、今回の実験の基点にはしない。
- 追加評価データ: `test/calibrated-function-calling-cases` の固定SHAから、指定fixtureだけを読む。
  ブランチ全体のコードや既存の別実験は取り込まない。
- ローカルcommitを残し、push・PR操作・本体への候補採用は行わない。

## 検討した構成と推奨

任意ファイルの編集や任意コマンドを許す汎用エージェントは、ユーザーが指定した2ツールの範囲を超える。
候補ごとに本体Pythonを書き換える方式は、採点や生成方式の変更を混ぜやすく並列化でも衝突する。
そのため、**固定した制御プログラムが、2つの指示文を持つJSON候補だけを受理し、
固定した評価処理を起動する構成**を推奨する。以下はユーザーの採用決定ではなく提案である。

## コンポーネントと権限

1. **改善用LLM**: 既存キャッシュのQwen3-0.6Bを初回の軽量モデルにする案。
   対象モデルと同じものだが、別の役割・会話・プロンプトとして実行する。
   モデルを追加ダウンロードせず、まず改善候補を作れるか確かめる。
   小さいモデルで有用な改稿が得られるかは未検証で、成功を前提にしない。
2. **制御プログラム**: LLMのJSON形式の操作要求をstrictなPydanticと共通JSONパーサーで検証する。
   利用可能な操作は次の2つだけ。モデルにOSのファイル操作・shell・Git・ネットワークは渡さない。
   - `write_prompt`: `name_instructions` / `parameter_instructions` の2文字列を受け取り、
     制御側が採番・ハッシュ化した候補ファイルを専用ディレクトリへ保存する。
     任意パス、追加フィールド、空の指示、既存ChatMLの役割を変える特殊タグは拒否する。
   - `run`: 保存済み候補IDの配布11件に対するGPU評価を要求する。
     コマンド・環境・評価集合・出力先・判定基準は制御側が固定する。
     LLMがCPU測定や追加評価データを直接指定することはできない。
3. **評価ワーカー**: 起動時に候補の2文字列を `src.prompt` の既存定数へ読み込ませる。
   Pythonソースは書き換えず、関数名・引数構造・マスク・greedy・256トークン上限を固定する。
   実験用エントリポイントだけが差し替えを行い、通常の `python -m src` はそのままにする。
4. **採点・昇格処理**: 独立したgoldを使い、モデルに正解判定を任せない。
   改善用LLMへは開発11件の結果だけを返す。追加33件の個別データは渡さない。
5. **記録**: 候補の全文・親候補・変更理由、モデルrevision、コードSHA、全入力hash、
   CPU/GPU環境、生成制限、並列数、生出力、エラー、採点、総時間と見積値を保存する。
   無効な改稿・上限終了・失敗した実行も残し、手書き候補をLLM生成と偽らない。

LLMの操作要求はデータとして読み、`eval` / Pythonコード生成の実行 / shell文字列への展開をしない。
これが権限の制限である。プロンプトに「編集禁止」と書くだけに頼らない。
モデルの利用は配布SDKの公開APIを使い、private APIやSDK本体を変更しない。
初回は既存GPU環境を再利用し、提出アプリの依存は増やさない。

## 実行順と採点

1. 起動前に元実装の更新を確認し、入力・gold・固定設定・候補のhashを記録する。
   配布例の正解は既存記録と依頼文から独立に確認し、モデルの予測を正解にしない。
2. GPUで元の指示文を評価し、**今回のコード・モデルでの基準値**を得る。
   過去の10/11は参考値で、今回の基準測定の代わりにしない。
3. 改善用LLMが開発例の失敗と現在の指示から改稿し、`write_prompt` / `run` を呼ぶ。
   候補ごとに同じ11件を評価する。初回の提案予算は2候補並列・4ラウンド、最大8候補とする。
   各ラウンドの全ワーカーの結果を回収してから次へ進み、共有の採用候補を同時更新しない。
   これは探索費用を有限にする開発上の初期値で、Subjectの制限ではない。実行設定に明示する。
   JSON操作が壊れた場合は理由を返して1回だけ再試行し、なお壊れる場合はその提案を失敗として残す。
   改稿出力の暫定上限は512トークン。上限で完結しないJSONは保存しない。
   同一候補hashの再提案は新たな問題や改善候補に数えない。
4. 完了・スキーマ適合を維持し、配布11件の**完全正答件数が厳密に増え、既存正答を失わない**候補を
   改善候補とする。11/11など改善余地がない場合は成功を捏造せず、同点候補の入力短縮を別に記録する。
5. 予算終了、またはラウンド終了時に11/11へ到達した時点で探索を終える。
   開発11件の条件を通る中から正答件数が最大の**1候補だけ**を選ぶ。同点なら候補IDの早いものにする。
   この選択に追加33件の情報を使わない。その候補の全文・hashを固定し、自分たちのGPUモデル処理をすべて止める。
   CPU 0〜15へのaffinity、6スレッド、MemoryMax=16G、MemorySwapMax=0、GPU無効、
   オフラインの既存モデルキャッシュで、実験用エントリポイントから**CLI全体**を単独実行する。
   候補の指示を読み込んだ後は既存CLIの処理を呼び、モデルのロードと保存も総時間に含める。
   既存 `research/evo-x3/measure.sh` の設定を再利用し、`CMM_OMP_THREADS=6` を指定する。
   このスクリプトに開発用のモジュール指定を追加し、許可値を既存の `src` と新しい
   `tools.prompt_trial` に限定する案とする。既定値は `src` のまま、その他の文字列は起動前に拒否する。
   `tools.prompt_trial` は候補を読み込んだ後、既存CLIを呼び、入力検証・出力準備・モデル起動・
   保存・終了コードを同じ経路で実行する。
   実験用エントリポイントへ渡せる最小限の実行経路を用意し、元の既定動作を変えない。
   生の実測を保存し、**総時間に1度だけ8秒を足す**便宜的な校舎見積値を別欄へ書く。
   待機は加えない。CPU結果とGPU結果の型付き値が一致するか、意味の採点も確認する。
   CPUで失敗・精度低下・300秒以上の見積値なら採用候補にせず、差を記録する。
6. CPU確認を通った候補を固定したまま、追加のoriginal/transfer/booleanをGPUで評価する。
   追加評価を開くのは、選んだ1候補と基準の対比較として一度だけにする。CPU確認で失敗した場合は、
   別候補の追加評価へ移らず、初回探索をそこで停止して理由を報告する。
   元の指示文も同じ33件で評価して、セット別・関数別・型別に対比較する。
   この追加評価の結果で自動的に改稿へ戻らない。結果を見た再調整は評価集合の用途変更を伴う。
7. 改善なし・予算終了・実行失敗も正常な停止理由として報告する。
   プロンプトを本体へ自動採用せず、候補と差分と結果を人が確認できる形で残す。

昇格でいう完全正答は、関数名・引数キー・型を区別した全引数値が固定goldと一致することとする。
数値は数学的な十進値で比べ、文字列は空白も含めて一致させ、真偽値を数値と同一視しない。
正規表現も昇格の主得点ではgoldの文字列と一致させ、動作一致は補助得点とする。
この既存の厳密な基準は別解を落とし得るため、表記だけが変わった改善を意味的な改善と呼ばない。
主得点を変える実験は事前に定義し直し、実行途中には変更しない。

正答・JSON/スキーマ適合・完了を別々に記録し、すべての分母に入力総数を含める。
正規表現は既存goldに対する文字列一致と、提供 `regex_checks` での動作一致を別々に測る。
`source_string`・`replacement`・関数名・型・引数キーは厳密に比較し、正規表現だけの別解と
空白の混入を混同しない。正規表現の実行は別プロセスで時間制限し、時間切れも失敗として残す。
可換引数の扱いは[データレビュー](../../research/calibrated-fixture-review.md)の注意に従い、
主得点の定義を実験結果を見て変更しない。

## 並列GPUと時間測定

ホスト環境の読み取り確認では、torch `2.14.1+rocm7.2`、GPU `Radeon 8060S Graphics`、
可視メモリ107374182400 bytes（100 GiB）、確認時空き107369951232 bytesだった。
これはモデルのロードや並列推論の検証ではない。GPUでの複数プロセス利用は少数並列で試す。
2ワーカーは初期の運用案であり、同時実行できるメモリ量や処理速度は実測前に保証しない。
候補ごとに出力・会話・設定を分け、共有Pythonファイルを編集させない。
OOMは記録して停止・逐次再試行する。逐次への変更を隠さず、探索の並列数を記録する。
GPUの並列実行時間は精度実験の経過であり、CPU性能や候補の速度比較に使わない。
CPU測定中は改善用LLMも止め、CPUとGPUの共有メモリへの自分たちの競合を避ける。
追加33件へも見積式を表示する場合は、既知の11件で作った固定補正の範囲外であることを明示する。
初回の必須CPU確認は配布11件であり、33件の校舎実行時間を保証しない。

## 本体更新の取り込み

ユーザーは `feat/implementation` の更新を実験ブランチに取り込むよう指示した。
現在のworktreeがクリーンで、候補評価プロセスがない境界でfetchし、対象ブランチをローカルmergeする。
ローカルの同名ブランチがremoteより先に進んでいる場合も確認し、未pushのcommitを取りこぼさない。
どちらか一方が他方の祖先なら新しい方を使い、分岐している場合は勝手に選ばず停止して理由を示す。
作業ツリーに他人の未commit変更があれば上書き・stashせず停止する。
merge conflictは自動で内容を決めず、実験を止めて報告する。

評価中に更新を検知してもコードを変更せず、そのラウンド完了後に取り込む。
merge後に既存テスト・lint・基準GPU評価をやり直し、有力候補も同じ新しいコードで再評価する。
異なるコードSHAで得た基準値と候補値を改善の根拠にしない。履歴はSHAごとに残す。
通常起動の冒頭とラウンド間に同期し、常駐監視や実験ブランチの自動pushは追加しない。

## 実装の範囲と検証

開発専用の制御・候補モデル・実験用実行経路・テスト・使用手順を追加する。
本体の生成方式、SDK、gold、入力、通常のCLI動作は変更しない。
新しい永続サービスや外部APIは使わない。開発資料はREADMEではなくdocsへ置く。

実装前に、2操作の権限制限、不正なJSON/余分な操作、候補の衝突・重複、固定された採点、
改善の昇格条件、CPU設定と加算の分離、追加データの非開示、コード更新で基準値が無効になること、
停止・再開・実行失敗を、固定応答と小さなデータでテストする。
実装後は `make install`・`make lint`・`make test` と独立レビューを実施し、実モデルの
並列GPU smoke test、基準、有限の探索、条件付きCPU/追加fixture確認をそれぞれ記録する。
未達の段階を実行済みとは報告しない。

## 根拠と未検証の点

既存の[プロンプト仮説](../../research/prompt-hypotheses.md)のH01〜H04を初回の説明に使える。
[ProTeGi](https://aclanthology.org/2023.emnlp-main.494/)は、誤りのフィードバックによる改稿と
評価による候補選択の参考であり、この小型モデルでの効果を保証する根拠ではない。
[Qwenモデルカード](https://huggingface.co/Qwen/Qwen3-0.6B)はツール利用・非推論モードの情報源だが、
ツール要求を守る精度やプロンプト改善能力はこの実験で確認する。
本体の基盤レビュー承認、未知のレビュー入力に対する90%以上の達成、CPU性能の厳密な再現は、
このワークフローを作っただけでは成立しない。
