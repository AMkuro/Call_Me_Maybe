# 校舎PCの連続負荷・熱監視

状態: ユーザーが2026-11-11に、自動的に温まる過程の測定、安全停止、VMを候補に含める方針を承認。
以下の閾値・CLI・固定SDK負荷は実装上の選択であり、ユーザーが個別に指定した値ではない。

## 目的と範囲

Subject v1.7 V.5の全プロンプト5分未満を検証するため、校舎CPUの温度と性能変化を調べる。
人が冷間・温間を作り分けず、同じ負荷を連続実行して温度の時系列と処理時間を採取する。
負荷は公開SDKのCPU forwardを固定入力長で反復する。16/64/256トークンを順番に繰り返し、
異なる入力長の速度を混ぜない。初回処理はwarmupとして残し、定常反復とは分ける。
これはSDK負荷の診断であり、実アプリの終了時間やSubject合格の証明ではない。

`origin/develop`にある`tools/campus_survey.py`の環境調査・匿名ID・モデルキャッシュ検出を再利用し、
`thermal`モードから`tools/thermal_survey.py`へ委譲する。未統合のhardware_probeやsrcの実装を持ち込まない。
`inspect`・`benchmark`の挙動とレポート形式、SDK、依存関係は変えない。

## CLIとデータ

```sh
python3 -m tools.campus_survey thermal \
  --hf-home /path/to/existing/huggingface --output /tmp/campus-thermal.jsonl
```

- Python 3.10+、Linux。モデルはQwen3-0.6B、`device='cpu'`、公開APIのみ。
- 所有者の指示によりPC IDは既定で既存の鍵とhostnameからHMAC生成する。`--pc-id`は任意の明示指定だけに使う。
  鍵の読み取りは既存機能を再利用し、未作成なら既存の`--init-hmac-key`で初期化する。
  `--hmac-key-file`で既存鍵を指定でき、鍵・hostnameの生値は保存しない。
- `--lengths 16,64,256`（各1〜2048、2種類以上）、`--duration 300`秒、全体の`--budget 360`秒。
- `--threads`は明示した場合だけ設定する。既定は継承し、設定値を記録する。
- 2026-11-11の再測定指示により固定85℃とcritの10℃手前の停止を廃止し、thermal counterの増加を主な停止条件にする。
  CPU固有のcrit値は緊急停止として維持する。critが読めない場合は開始しない。
  `--max-temp-c`は任意の追加上限（1〜150℃、既定なし）で、CPU固有critを引き上げられない。
  `--min-free-mib 1024`（512以上）は維持する。
- 監視間隔0.5秒。モデルロード中、forwardが戻らない場合も親が監視する。
- モデル取得・自動インストールをしない。既存キャッシュがなければ負荷を開始しない。
- JSON Linesを排他的に権限600で新規作成し、上書き・symlink追従をしない。
  metadata、sample、warmup/forward、stage、summaryを逐次flushする。
  summaryがなければ未完了。途中停止した測定も成功と区別し、途中までの記録を残す。
- 各forwardは入力長、開始からの経過ナノ秒、所要ナノ秒を記録する。
  JSONLを全保存し、入力長ごとの全体中央値と、最初/最後の5回の中央値の比を要約する。
  10回未満の場合は前後の比を出さない。外れ値を削除しない。
- metadataは既存surveyの公開レポート検査を通した環境情報、匿名PC ID、UTC、commit、SDK・lock・調査器のハッシュ。
  入力は固定の公開文で、プロンプト本文、環境変数一覧、ユーザー名・hostname・ホームパス・生の例外は保存しない。
- CPU温度をセンサーごとに保持する。周波数は取得元と値を記録し、実効周波数と断定しない。
  RAPL電力量と上限・時間窓、CPUのSMT/コア対応、メモリとcgroupの制限も読める範囲で記録する。

## 安全停止

起動前の観測をbaselineとし、以下で負荷を開始しない、または直ちに中止する。

1. coretemp/k10temp等のCPU温度が取れない、値が不正、既存のセンサーが読めなくなる。
2. Intelのcore/package thermal throttle counterが取れない、読めなくなる、減少する、baselineより増える。
   カウンターごとに比較し、合計を独立した事象数にしない。
3. counter増加がなくても、CPU固有のcrit値、または明示された追加温度上限へ達したら緊急停止する。
   同じ観測でcounter増加とcrit到達があれば、thermal_throttlingを終了理由にする。
4. MemAvailable、または読めるcgroup v2の残メモリが指定の余裕未満になる。
5. 全体予算超過、SIGINT/SIGTERM、子の失敗・異常終了、レポートの書き込み失敗。

熱制限カウンターがないAMDや、ホストのセンサーが見えないVMゲストでは、検知不能を成功扱いしない。
CPU時間割当によるcgroupの待機は熱スロットリングとは別記録であり、意図的なCPU制限を熱異常と誤判定しない。
周波数低下だけで熱が原因とは断定しない。CPU・ファン・電力上限等の設定変更や自動再開はしない。

子は専用プロセスグループで起動する。中止時はSIGTERM、1秒後に残ったグループへSIGKILLし、回収する。
親が受ける停止シグナルは子へも反映する。監視とIPC受信を別の時刻で管理し、
子から結果が頻繁に届いても安全監視が後回しにならないようにする。
この監視は0.5秒間隔のソフトウェア対策で、急変や物理故障を防ぐ保証ではない。

終了コードは0=指定期間完了、1=測定/子/書込失敗、2=引数不正、3=起動前の条件不足、
4=安全停止/予算超過、130=SIGINT、143=SIGTERMとする。
温度・counter・メモリが不足する場合に検査を無効化するオプションは設けない。

## VMと次の検証

VMはOS分離に加え、vCPU・メモリ・swap・依存をまとめて管理できる点も含めて、cgroupと対等に候補とする。
ホストで物理温度・熱制限を監視し、ゲストで固定負荷を計測する構成を検討する。
今回のコマンドは両者を遠隔制御する機能を持たない。センサーがないゲストで単独実行して安全確認済みとはしない。
KVMのデバイス・権限、センサーのホスト/ゲストでの可視性を確認してから構成を決める。
AMD上のVMでIntelのキャッシュ・冷却・P/Eコアを再現したとは扱わない。

テストは偽のsysfsと固定logitsを使うSDK、実際の子プロセスで行う。
熱を実際に上げたりスロットリングを発生させたりして停止テストをしない。
校舎で本ツールを実行して初めて実際の温度曲線を確認できる。
既存のphys16-t6総時間＋8秒の方針は変更しない。新しいraw値への加算やsleep挿入はしない。
